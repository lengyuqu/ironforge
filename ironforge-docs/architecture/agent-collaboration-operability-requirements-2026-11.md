# 多 Agent 协作：规则入口、用户总览、恢复与完成条件

> 状态：Proposed，待评审；2026-11-04。补充[产品需求](agent-collaboration-product-requirements-2026-11.md)，并与[实施路线图](agent-collaboration-implementation-roadmap-2026-11.md)、[P0](agent-collaboration-p0-design-2026-11.md)、[P1](agent-collaboration-p1-design-2026-11.md)、[P2](agent-collaboration-p2-design-2026-11.md)配套。本文定义需求和候选契约，不表示功能已实现或验证，也不改变首版在制任务。

## 1. 定位与优先级

| 需求 | 建议优先级 | 最早依赖 | 用户价值 |
|---|---|---|---|
| O01 协作规则入口 | P0 并行 | 首版基线及 Git 按 SHA 读取 | 新 Agent 能定位本仓规则、适用范围和版本 |
| O02 用户总览 | P0 分批 | 首版任务/会话/交接；完整问题答复依赖 P0-2/P0-4 | 用户能发现阻塞、待决事项和需要接手的工作 |
| O03 保留与恢复 | P0 先核验，恢复能力分期 | 首版数据模型及现有备份链路的事实核验 | 删除或故障后，数据影响与恢复能力可判断 |
| O04 任务完成条件 | P1 展示优先 | 首版任务；问题条件依赖 P0-2，证据条件依赖可验证 CI 关联 | 区分 Agent 声明与可检查的完成条件 |

P0 表示优先处理，并不自动变更已规划的 P0-1–P0-5 内容或给出部署授权。任务按依赖分别交付；O03 的现状审计不能等到 P2，真正恢复由安全的测试环境和真实链路验证。

## 2. O01：协作规则入口

**用户场景**：Agent 第一次接手仓库或跨会话恢复时，不必靠猜测查找 `AGENTS.md`、项目约定、构建命令和风险边界；它能知道这些信息来自哪个 commit，且路径适用于哪些文件。

### 行为与候选接口

`GET /api/v1/repos/{owner}/{repo}/collaboration/rules?ref=<branch-or-sha>&path=<relative-path>&cursor=...`，要求仓库读权限。响应建议包含 `requested_ref`、`resolved_commit`、`path`、`entries[]`、`next_cursor`、`truncated`、`discovery_version`。每条 entry 包含仓库相对 `path`、blob SHA、适用目录、发现来源、优先级说明、读取地址及可信度标记。所有文件内容均为 `origin=repository_content`，平台只描述位置和配置，**不声称仓库文本拥有系统指令权威**。

仓库可在版本控制中的 `.ironforge/agent-context.toml` 明确声明入口、范围和顺序；未提供时采用公开、版本化的默认发现规则：根目录 `AGENTS.md`、沿目标路径向下的 `AGENTS.md`，以及显式配置的项目文件。`CLAUDE.md` 等工具专用文件仅按配置或客户端声明发现；不能假设所有 harness 都自动遵守同一文件。实际覆盖、继承、工具专用规则和用户指令优先级在响应中保留来源，由调用方依据自身执行环境决定；服务端不合并或重写指令。

首次解析 ref 得到 commit，后续分页和读取使用该 SHA；游标绑定仓库、commit、目标 path、规则版本与筛选，失效或对象不可读时明确报错。`path` 使用规范化仓库相对路径，不跟随符号链接越出仓库，不解释文件中的外部链接。限制条数、文件大小和深度，显示截断及后续读取位置；无权限返回现有仓库权限错误，不为私有仓库泄露存在性。

工作上下文可记录 `rules_commit` 与 entry blob SHA；比较时将 branch 重新解析并返回 `unchanged/changed/unknown`。分支变动不应将已固定快照静默替换成新内容。规则内容是仓库维护者提供的数据，可能存在指令注入；客户端仍需按自身指令层级与工具授权处理。

### 数据与实施边界

首期无需新增独立规则表：版本内容存 Git，动态解析；任务保存规则快照引用可选，涉及新增持久字段时单独评审迁移。manifest schema、默认路径、权限与排序需与现有客户端习惯核对；本提案不改变 Codex/Claude 的原生文件发现行为。

### 验收 O01

1. 根和子目录各有规则文件；对两个不同路径给出正确适用项、来源、顺序与 SHA，两个客户端一致。
2. 读取第一页后推进分支，后续读取仍绑定原 SHA 或明确失效；旧任务比较结果为 changed/unknown，不混合内容。
3. 超长文件、深层目录、分页、非法路径、符号链接及仓库撤权均有明确结果，不越界或泄露。
4. 不同客户端收到同样可验证的来源，但仓库内容不能自动获得系统级权限；不存在的可选文件不会伪造规则。

## 3. O02：用户协作总览

**用户场景**：用户打开一个仓库，即可知道哪些任务在进行、哪些问题等待自己、哪些工作因离线或交接停滞，并能进入上下文答复。

### 页面与候选接口

单仓库先行，候选 `GET /api/v1/repos/{owner}/{repo}/collaboration/overview?sections=...&limit=...`。汇总任务状态、活跃/离线会话、待答问题、pending handoff 和最近活动；响应的每个 section 带 `items`、`as_of`、`truncated`、`next_cursor`，每项指向原始 task/question/handoff，不直接复制完整聊天。默认显示：**待我答复、阻塞与等待、待接手交接、进行中的任务**；计数和条目只包含当前用户有权读取的对象，首期不进行跨仓聚合。

用户可打开问题查看上下文与选项并按 P0 契约答复；可查看工作包中的 SHA、声明和平台验证结果；人工重指派按 P0 权限、版本和审计要求处理。总览本身不将在线视为正在工作、不将已读当同意、不将 Agent 的 done 当验证通过。会话在线状态是租约/心跳推导，显示时间和 unknown 状态。

首个切片只使用已完成首版的任务、会话和交接，不伪称支持问答；P0 问答与收件箱完成后增加待答事项。按各 section 的实际数据源版本返回；不存在跨 section 的原子快照承诺，执行写操作前重新读取对象和版本。列表翻页和权限检查沿用 P0 的快照契约；UI 不得显示其他仓库或无权对象的计数。Web 是建议入口；如先提供 CLI/其他人工客户端，完整用户验收仍要求真实用户可查看、答复和检查结果。

### 数据与验收 O02

首期复用现有对象和 P0 收件箱，不建立另一套状态；缓存如用于性能必须标注更新时间并重新鉴权。验收：真实用户看到不同状态且可定位原记录；离线/过期会话不被误标完成；问题答复竞态返回明确版本冲突；撤权后无对象、名称、计数泄漏；分页/截断和数据刷新状态清楚；慢请求、服务重启及空仓库有可理解反馈。

## 4. O03：保留、备份与恢复

**当前已记录事实**：[首版实施说明](multi-agent-collaboration-design-2026-11.md) §9 记载仓库或用户删除通过外键级联删除协作记录；[验证记录](multi-agent-collaboration-verification-2026-11.md)记载尚无协作记录保留期及清理。具体备份覆盖、删除实现和当前工作区行为须在动工时重新核对。已有备份功能的存在不能证明协作数据可恢复。

### 需求与候选契约

1. **影响预览**：管理员在执行仓库/用户删除前可查看本次可能受影响的任务、消息、交接、问题、工作包及其他协作记录的类别和数量。预览必须与执行条件及版本关联；状态变化时重新预览。用户只能查看其有权管理的对象；公开 API 和 UI 不暴露无权记录。预览不是授权也不执行删除。
2. **保留策略**：实例管理员配置保留期、归档/清理方式与适用范围；默认值需产品确认。展示当前生效策略及其来源。仓库删除、账号删除、软删除恢复与备份到期分别定义；保留策略不能悄然覆盖现有删除语义或法律/用户要求。
3. **一致性备份**：确定数据库快照、Git refs/对象、必要制品和配置的覆盖范围、版本/校验和和时间点；对象跨存储时建立可验证的备份边界与不一致检测。会话密钥明文不随备份导出；密码和令牌等敏感数据的恢复政策沿用并核验现有系统。备份完成只表示产物生成，不代表可恢复。
4. **隔离恢复**：将备份恢复到专门隔离的临时环境，校验迁移版本、对象引用、消息顺序、任务版本、交接及权限，真实 Git 对象 SHA 可读取；校验失败不替换现有服务数据。恢复后的旧会话是否失效、令牌策略和副作用抑制（邮件/webhook/CI）须明确，默认恢复演练不向外发送或执行。
5. **恢复报告**：记录产物标识、完整性、恢复目标、执行环境、软件版本、覆盖时点、实际验证结果和缺失项；提出建议 RPO/RTO 后再结合真实演练设目标，不把建议当已达成指标。

若新增 API，候选为管理员权限的 `POST /.../deletion-preview` 与 `GET /.../retention-policy`；实际路径需核对现有 API。备份与恢复优先复用已有运维入口，先盘点其一致性和权限；不新增可绕过现有认证的远程恢复端点。设计不授权删除、生产恢复、迁移或变更护栏。

### 验收 O03

- 测试库中构造跨表协作数据和 Git commit，预览删除影响；并发数据变化使旧预览失效。权限不足者不能查看影响细节。
- 真实备份产物恢复到隔离环境后，校验任务、消息顺序、交接、引用及目标 Git SHA；不发送外部通知、不触发 CI。损坏/缺失文件、版本不兼容和不一致快照明确失败并保留现有数据。
- 分别在支持的 SQLite、PostgreSQL、MySQL 上以实际支持的备份/恢复链路验证；无法获得真实后端或存储时标为待验证。核对会话、凭据、保留/删除语义，不以 mock 或仅测试导出替代恢复演练。

## 5. O04：任务完成条件

**用户场景**：Agent 声称 done 时，用户能看到哪些条件已满足、由谁声明、哪些证据缺失或已过期。

### 规则与候选接口

首期以**展示为主，不阻止修改任务状态**。任务可定义条件列表，每项有稳定 ID、类型、参数、创建者、版本及适用上下文。首批类型：

- `question_answered`：引用同任务的问题和答复，检查状态与上下文新鲜度；unknown/stale 不算 satisfied。
- `work_package_present`：引用同任务的工作包版本，只说明包存在，不证明其中所有声明属实。
- `ci_passed_for_commit`：指定仓库 commit SHA、检查名称及可验证的 pipeline/job 记录；检查记录必须由平台识别并绑定实际被测 SHA，跳过、取消、未执行、无权读取为 unsatisfied 或 unknown（分别标明），不能用 Agent 自述顶替。
- `manual_confirmation`：记录授权账号的明确确认和关联上下文版本；它是协作确认，不自动成为分支保护中的人类审批，也不因自报 `actor_kind` 证明是真人。

候选 `PUT /.../tasks/{id}/completion-conditions`（带任务期望版本和幂等键）设置条件；`GET /.../tasks/{id}/completion-status` 返回任务声明状态、条件版本、每项 `satisfied/unsatisfied/stale/unknown`、证据引用、评估时间及总体结果。该 API 不提供可用的 CI 数据时明确 unknown；新 head/base、工作包替换或问题上下文变化时重新评估，不把旧证据用于新版本。

条件定义与任务版本关系、历史版本和不可变评估快照需单独数据模型；不能只将动态查询结果当作历史证据。所有引用校验同仓库、权限和关联关系。未来若提供“条件未满足禁止 done”的强制模式，需单独评审权限、迁移、旧客户端兼容和故障时 fail-closed 行为；不能让该模式绕过既有分支保护。

### 验收 O04

1. Agent 自报 done，但没有有效证据时，用户可见声明与条件 unknown/unsatisfied；不伪称系统已验证。
2. CI 在 SHA A 通过，任务 head 更新到 B 后 A 的结果不能满足 B 的条件；取消/跳过/无法访问均不视为通过。
3. 问题答复上下文过期、工作包版本变化、并发修改条件均按版本返回 stale/冲突，历史可追溯。
4. 已有客户端仍可更新任务状态；展示模式不修改 Git、审批或任务状态。用户确认不等于真人审批。

## 6. 其余需求的后续位置

| ID | 需求与初步范围 | 建议阶段/依赖 | 立项时最低验收 |
|---|---|---|---|
| O05 通知升级 | 阻塞过久、失败或接收者过期后按用户配置提醒；静默窗口和去重 | P1；依赖 U04 持久通知 | 同一事件不重复轰炸；取消/恢复后不发过期提醒；不向无权用户推送 |
| O06 任务模板 | 定义目标、交付和验收清单，创建任务时固定模板版本 | P1；首版任务与 O01 规则版本 | 使用后保留版本来源；模板改动不静默改历史任务 |
| O07 能力/环境声明 | Agent 自报工具、测试能力和网络限制供协调 | P1；首版会话 | 过期标记与来源可见，不作为授权或可信身份 |
| O08 成本与资源预算 | 按任务记录可用预算及实际消耗；阈值提醒或经用户设置暂停 | P2；先明确各 harness 指标口径 | 单位/来源/采样期明确；缺失数据不伪报零；暂停不能丢未完成操作 |
| O09 协作记录搜索 | 按任务、问题、决定、交接和 SHA 检索 | P1/P2；依赖对应对象与权限过滤 | 索引新鲜度可见；撤权不泄露内容、计数或片段 |
| O10 故障诊断 | 区分离线、通知延迟、服务异常、权限撤销 | P1；依赖首版状态和 U04 通知 | 显示可验证来源和 unknown；不把无法判断的故障归因于 Agent |

## 7. 执行与验收记录

建议任务拆分：O01 规则发现与快照；O02 首版总览与完整问答接入；O03 现状审计、影响预览、备份一致性和恢复演练；O04 条件定义、平台证据关联与展示。具体顺序和依赖见[实施路线图](agent-collaboration-implementation-roadmap-2026-11.md)。

每项记录目标 SHA、工作区状态、命令、数据库/服务/客户端版本和证据位置，区分实现、任务测试、合并后集成、真实运行、远端和发布。SQLite/PostgreSQL/MySQL 的适用数据完整性分别验证；真实用户界面、双客户端和恢复链路的缺失项明确标记待验证。本文是设计文档，不以链接或静态检查通过替代业务验收。
