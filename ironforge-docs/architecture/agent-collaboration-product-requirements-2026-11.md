# 面向多 Agent 协作的产品需求补充

> 状态：需求建议，待评审；2026-11-04。与[协作首版设计](multi-agent-collaboration-design-2026-11.md)及[整合路线](harness-integrated-roadmap-2026-11.md)配套。这里描述期望行为，不表示已经实现或验证，也不改变正在实施的首版范围。

## 产品目标

多个 Agent、多个 harness 和用户围绕同一仓库工作时，应能发现未处理的事情、理解任务上下文、提出问题、协调依赖、交接结果。即使它们共用一个 Git 账号，也要能从协作记录看出是哪个会话作出的声明，并能找到与之相关的代码和验证证据。

账号是授权主体，会话是协作归属，不是可信身份边界。平台呈现的完成、测试或身份声明，应与可核验的平台事实区分；外部内容也不能自动转化为 Agent 的操作权限。

优先级仅用于评审：P0 为真实协作闭环关键需求，P1 为减少重复沟通和等待，P2 为扩大协作规模。首版已有能力标注为“沿用”，不要求负责实现的 Agent 临时扩展当前任务。

## 需求清单

| ID | 优先级 | 场景与需求 | 可观察的验收标准 | 首版关系 |
|---|---|---|---|---|
| R01 协作收件箱 | P0 | 会话重新上线后，一次看到分配给自己、@自己、待接手的工作和阻塞回复 | 返回可访问仓库内分组条目、目标、最新活动和跳转定位；已读/待处理独立；分页不遗漏，撤权后不返回 | 新增；首版任务消息和 handoff 列表可作为基础 |
| R02 问题与答复 | P0 | Agent 需要其他 Agent 或用户作决定，而不只是发送一条消息 | 问题有发起者、接收范围、状态、答复与关联任务；可区分等待、已回答和已撤销；重复提交不创建两份 | 新增；不将普通已读误当答复 |
| R03 离线接手 | P0 | 原会话过期、密钥丢失或设备不可用，另一会话继续任务 | 新会话能查看当前任务、消息、交接与待决问题；能申请或声明接手，历史保留；不依赖旧密钥或让旧会话复活 | 扩展首版交接；接手只是协作归属，不授予 Git 权限 |
| R04 用户决策入口 | P0 | Agent 被产品选择或权限问题阻塞时，用户能看懂并答复 | 用户能从任务看到问题、选项、影响和上下文版本，给出决定；变更后的上下文使旧决定标记待复核 | 新增；人工 UI/API 体验独立设计；协作答复不等同受保护分支审批 |
| R05 工作包与结果 | P0 | Agent 完工后，接手者无需翻完整聊天就知道交付了什么 | 一份工作包包含目标、范围、产物链接、SHA、未解决项、验证记录和下一步；标识声明、平台事实和缺失项；可以查看源记录 | 扩展首版 handoff；不要求先实现完整证据平台 |
| R06 任务依赖 | P1 | 一个任务等待另一个任务的结果 | 显式建立依赖并显示阻塞原因；防止循环；依赖完成后提示相关会话，由其决定继续 | 新增；状态变化不自动执行代码 |
| R07 协作上下文包 | P1 | 新 Agent 加入或长对话压缩后，要低成本恢复状态 | 按预算返回目标、当前状态、未答问题、最近决定、交接和关联代码版本；每项有来源、时间、截断提示及原文定位；不虚构摘要 | 扩展整合路线预算读取；模型生成摘要须标注并可回溯 |
| R08 冲突预警 | P1 | 多个 Agent 同时修改同一文件或关联任务 | 展示声明路径与分支的重叠，提示来源和更新时间；过期声明标记不确定；提示不阻止写入且不替代 Git CAS | 已列为协作增强 |
| R09 消息送达与通知 | P1 | 消息发出后，发送者想知道对方是否看见或答复 | 区分已保存、目标已读、已答复；离线重连可恢复；不把已读视作同意；通知按会话和仓库权限隔离 | 扩展首版已读；推送只是可选加速 |
| R10 交接可靠确认 | P1 | 原 Agent 交接后仍需知道新 Agent 是否接受 | 展示 pending/accepted/cancelled 和目标；并发接受/取消只出现一个终态；目标会话过期可重新指派，保留历史 | 沿用并扩展首版 handoff |
| R11 可追溯决定 | P1 | 多轮讨论之后要知道采用了哪个方案及原因 | 决定记录关联问题、依据、答复、参与会话和相关 SHA；后续可追加替代/撤销记录，历史可查 | 新增；与代码保护审批分开 |
| R12 多仓库关联 | P2 | 改动跨服务或多个仓库，不能在每个仓库复制上下文 | 任务可链接到多个获授权仓库及各自 SHA；权限不足的部分不泄露名称、内容或计数 | 新增；先解决跨仓授权与删除语义 |
| R13 协作健康 | P2 | 用户希望了解哪里长期阻塞或重复返工 | 展示等待时长、阻塞原因、交接次数及过期声明；区分自动采集与自报，允许按任务钻取；不以活动量排名 Agent | 新增；先明确保留期和可见范围 |
| R14 可迁移互通 | P2 | 不同厂商的 harness 在中途接力 | 提供版本化 REST/MCP 契约、能力发现和示例；未知可选字段不导致旧客户端失效；不同客户端可读取同一任务并接力 | 在首版 REST/MCP 的契约测试基础上扩展 |

## 产品规则与典型流程

1. **会话与工作分离**：任务、待答问题和交接属于仓库内持久工作记录，不随某个会话在线状态消失。会话离线或过期只能说明其不可用，不能据此判定任务失败、结束或交接完成。
2. **已读、答复和授权分别表达**：已读只说明查看进度；回答说明对问题的反馈；操作授权及合并批准由原有权限和保护机制单独判断。
3. **接手先看状态再继续**：Agent B 在收件箱发现阻塞 → 打开任务和代码版本 → 查看尚未解决的问题、现有交接与证据 → 声明接手 → 回答或请求用户决策 → 写下新的工作包。每个动作保留来源，避免单靠同账号用户名判断是谁。
4. **状态不等于事实**：Agent 可声明“测试通过”，但必须显示为自报；如果链接了 CI 记录，分别展示被测 SHA、状态和来源。没有可核验记录时显示未提供证据。
5. **共享账号的限制可见**：同一账号的其他客户端可能注册同名会话；任何展示名称、模型名称、任务标签都不能作为可信身份证明。需要更强隔离时依赖独立受限凭据。
6. **权限和内容安全**：列表、聚合与通知逐项遵守仓库授权；引用的外部内容和消息是数据，不自动触发工具、通知外发或代码变更。日志与摘要不得包含会话密钥。

## 建议实施顺序

- **首版完成后先验证**：用两种真实客户端完成首版会话、消息、交接和断线恢复；记录操作步骤、失败点和用户需要手动复制的信息。
- **下一批 P0**：先做收件箱与离线接手（R01、R03），随后增加结构化问题、用户答复与工作包（R02、R04、R05）。接口和 UI 分别验证，但无需等待完整 Git 写工具或统一事件系统。
- **再做 P1**：基于真实沟通记录设计任务依赖、上下文包、送达状态与决定记录；路径冲突提示与已有计划协调，避免重复实现。
- **P2 按需求触发**：先确认跨仓使用和评估需求，再设计多仓权限、指标和跨客户端互通；不预先建设完整调度平台。

建议首批产品验收包含：两个 Agent 同账号、一人离线、另一人接手、向用户提问并获得答复、关联真实提交与验证结果、切换会话后继续。统计首次找到待处理事项的请求次数、恢复交接所需步骤、未答问题遗漏数；先记录基线，再设量化目标。真实客户端和真实仓库未运行时，标记待验证。

## 待产品确认

- 收件箱默认覆盖当前仓库还是用户可访问的全部仓库？跨仓聚合会增加权限过滤与查询成本。
- 用户希望在 Web UI 直接回复，还是优先由 CLI/MCP 转达？两者都可规划，但会影响首批交付顺序。
- 协作消息对所有仓库读者可见，还是仅对写者或参与者可见？涉及已有首版权限契约，应在实现变更前单独评审。
- 问题是否必须指定唯一接收者，还是可面向用户或多个会话？首版设计应明确无人响应和接收者失效的语义。
