# 多 Agent 协作 P2：跨仓关联、协作健康与客户端互通

> 状态：Proposed，待评审；2026-11-04。细化[产品需求 R12–R14](agent-collaboration-product-requirements-2026-11.md)，与[首版设计](multi-agent-collaboration-design-2026-11.md)、[P0](agent-collaboration-p0-design-2026-11.md) 和 [P1](agent-collaboration-p1-design-2026-11.md)配套，不改变它们的在制范围。
> 本次为设计和静态核对：当前 `collab_tasks` 有单一 `repo_id`；`rg-mcp/src/main.rs` 的 initialize 写有协议版本，工作区 MCP 修改仍在进行。以上不是运行验证；实施前以最终合并代码为准。

## 1. 目标和边界

- **R12**：跨服务任务能关联多个仓库的实际任务和提交，同时遵守各仓权限，不暴露无权访问的仓库、名称、SHA、数量或活动。
- **R13**：让用户发现阻塞、交接等待和过期声明；指标可追溯到记录，区分平台计算与 Agent 自报，不给 Agent 排名。
- **R14**：不同 harness 可通过可发现、版本化的 REST/MCP 契约接续工作，离线后按公开恢复语义重连。

默认单实例数据库语义适用于同一 IronForge 实例。跨实例或外部 GitHub/Gitea 联邦、跨仓全局自动调度与服务端 LLM 不在首批范围；先以两个真实客户端和两个仓库的用例验证价值。P2 是候选路线，不表明 P0/P1 已实现。

## 2. 身份、权限与通用契约

账号是授权主体，会话是协作归属；相同账号的展示名可冒用，不能据此证明真实人类或独立 Agent。每次请求和分页分别对可访问资源重新授权；对跨仓数据逐仓判定，不能只检查入口仓库。私有仓库无权限时，响应、聚合计数、游标、错误和日志均不揭示其存在。仓库权限缓存及多实例撤权延迟沿用当前系统的实际语义，测试并明确报告；不可宣称即时撤权。

本方案的用户输入、任务标题、评论、路径和外部链接均是不可信数据。禁止自动抓取外部链接或依内容执行操作。REST 错误沿用现有 envelope，机器可读 reason 和版本为提案；兼容规则见第 6 节。所有新增写操作沿用 P0 的请求 ID、主体和动作范围、规范化请求哈希、事务内唯一约束与 30 天保留建议；同体重试返回同一结果，异体 409，重试重验授权。有关新迁移、数据和权限变更按项目护栏办理。

## 3. 数据模型

名称为候选，沿用现有仓库、用户、会话和任务主键类型，跨对象引用需检验所属仓库。数据库必须支持 SQLite、PostgreSQL、MySQL；不修改已执行的迁移。

| 候选对象 | 主要字段 | 约束与生命周期 |
|---|---|---|
| `collab_coordination_groups` | `id`, `anchor_repo_id`, `title`, `description`, `created_by`, `version`, `created_at`, `updated_at` | 内容必须为跨仓可分享的通用说明，视为锚仓数据；禁止服务端自动写入其他仓库名称、标题或私有内容；任务原数据仍在各自仓库 |
| `collab_coordination_links` | `id`, `group_id`, `target_repo_id`, `target_task_id?`, `commit_sha?`, `created_by`, `created_at`, `removed_at?` | 同一 group/repo/task/commit 活跃关联唯一；所有对象同一实例；commit 使用完整 SHA 并验证属于目标仓；审计记录引用但不复制内容 |
| `collab_metric_events` | `id`, `repo_id`, `task_id`, `event_type`, `from_state?`, `to_state?`, `source_type`, `source_id`, `occurred_at`, `recorded_at` | `(repo_id,source_type,source_id,event_type)` 唯一；由业务服务同事务写入，不存密钥或消息正文；不假设 ID 顺序等于提交顺序 |
| 可选 `collab_metric_rollups` | `repo_id`, `bucket`, `metric_version`, `counts_json`, `computed_at`, `source_checkpoint` | 纯缓存，可由事件重建；不得汇总后绕过逐仓权限，也不得把未覆盖数据算成零 |
| 可选 `collab_group_snapshots` | `id`, `principal_id`, `anchor_repo_id`, `filter_hash`, `items`, `created_at`, `expires_at` | 只保存建立时授权可见的关联 ID 和排序键；共享存储、短 TTL；翻页仍逐项重新鉴权；不可充当权限凭据 |

系统记录与用户自报分别标注 `source=platform_event` / `user_content`。不引入不可审计的隐藏主体。具体表、索引和存储期限在容量验证后定稿。

## 4. 跨仓关联 R12

### 权限模型

采用**锚仓工作组 + 仓库级关联**：group 归锚仓所有；查看 group 需要锚仓读权限，查看每个 link 还需目标仓读权限。创建 group 需锚仓写权限；新增或移除 link 需同时拥有锚仓和目标仓写权限（以及有效 Agent 会话，如调用方是 Agent）。不支持“只凭 group ID 访问目标仓”。单仓任务仍归原仓管理，跨仓组不转移任务、扩大 Git 权限或形成 P1 跨仓依赖边。

服务端**先授权、后排序和分页**；对不可访问目标静默过滤，响应中的数量、`has_more`、游标及页长度只反映可见集合，不返回“有隐藏项”的标记。锚仓的 group 标题、正文、任务消息是锚仓读者可读内容；无法阻止用户自行在自由文本写入其他仓库信息，因此界面应提示创建者按锚仓权限共享，且服务端不自动把目标仓信息复制到这些文本、审计公开描述或通知。强保密信息不能放在较宽权限的锚仓正文。

### 接口

| 方法 / 路径 | 请求与语义 |
|---|---|
| `POST /api/v1/repos/{owner}/{repo}/collaboration/groups` | `{client_request_id,title,description?}` → group；锚仓写权限 |
| `GET /api/v1/repos/{owner}/{repo}/collaboration/groups/{group_id}` | → group 公共字段及当前可见 links；大集合使用下方分页，不返回隐藏总数 |
| `POST .../groups/{group_id}/links` | `{client_request_id,target_repo_id,target_task_id?,commit_sha?,expected_group_version}`；双仓写权限；事务内校验任务归属、commit 格式和目标仓对象存在，CAS group 版本 |
| `GET .../groups/{group_id}/links?limit=&cursor=` | → `{items,next_cursor,has_more,as_of}`；仅可见关联；每页重验锚仓和目标仓权限，返回时 resolve 当前名称而非持久化旧名称 |
| `DELETE .../groups/{group_id}/links/{link_id}` | `{client_request_id,expected_group_version}`；双仓写权限；软移除并审计，重复同键安全 |

锚仓相对路径 `...` 同上表第一行的 `/api/v1/repos/{owner}/{repo}/collaboration`。GET 列表默认 50、最大 100，按创建时间和 ID 排序。第一页建立 10 分钟有界可见 ID 快照并绑定账号、锚仓、group 和筛选；后续逐项重新授权并过滤失权项，不返回失权原因或隐藏数量。新增授权/新增链接由新快照发现，已有快照不扩容。若最后可见项被撤权导致空页，服务端内部继续扫描直到填满或耗尽，不能把空页误称完成；过期返回 `CURSOR_EXPIRED`。快照上限初议 1000 个**可见**链接，超过显式提示收窄筛选，不暴露隐藏链接数量。多实例使用共享快照或明确要求重启分页，不使用本机内存保证一致性。

创建/移除与 group 版本更新使用同一 DB 事务；并发同一版本仅一方成功，重试遵守幂等契约。检查 Git commit 与 DB 提交无法原子化：校验目标 commit 可读并记录其 SHA；Git 对象后续被 GC 时返回 `commit_state=unavailable`，不回退其他 SHA。若要求长期可重放，另行设计对象保活及存储配额，首批不承诺。

仓库重命名用稳定仓库 ID 定位，展示当前名称；软删除或仓库不可读时 link 从可见列表消失。锚仓删除后不能通过 group 路由访问，恢复后是否恢复 link 遵循仓库恢复策略；目标被恢复后重新授权可重新显示。关联记录及审计的保留/物理删除遵循实例政策，不能因删除提示泄露曾有隐藏仓库。并发撤权与链接写入以事务隔离和实际权限缓存语义为准，需专门验证。

## 5. 协作健康 R13

### 定义与口径

指标仅按**单个有权访问的仓库**提供，默认要求仓库管理员权限；普通成员可见性为待决产品选择。区间 `[from,to)` 使用 UTC，最大 90 天，默认最近 7 天，返回 `metric_version`、计算时间、事件覆盖起点、时区和区间。禁止以会话、模型或 Agent 排名；只按任务钻取，用户可自己查看证据。

| 指标 | 精确定义 | 数据来源与限制 |
|---|---|---|
| 阻塞任务数 | 截至 `to` 处于 `blocked` 的任务数，及在区间内曾进入 blocked 的任务数分别返回 | 任务状态是自报；不同概念不得合并；已删除/不可见任务按既定保留政策处理 |
| 阻塞时长 | 每个 blocked 区间与 `[from,to)` 的交集秒数之和；未结束区间截到 `to`，标注右删失 | 使用服务端状态变更事件；非首次完整观察标注左删失，不夸大为完整持续时间 |
| 交接等待 | handoff 创建到 accepted/cancelled 的区间交集，pending 截到 `to`；分别给出接受、取消、未完成数量 | 使用首版 handoff 事件；接受不等于完成工作 |
| 过期路径声明 | 截至 `to`，未完成任务中路径声明时间早于配置阈值的数量 | 依赖 P1 独立路径声明时间；缺字段返回 unknown，不用任务通用更新时间替代 |
| 等待问题数 | 截至 `to` 仍 open 的问题及等待时长 | 依赖 P0 问答事件；非真人身份证明 |

平台事件采用事务内记录业务状态变化；事件时间由服务端写入，禁止用客户端时间作为权威。历史功能上线前不具备完整事件流：响应返回 `coverage_start` 和 `partial=true`；可以设置一次性初始快照，只能作为观察起点，不能伪造此前历史。负时间、缺事件或不一致数据标为 `unknown` 并提供质量计数。对不具备有效基线的数据不输出精确历史时长。

### 接口和展示

`GET /api/v1/repos/{owner}/{repo}/collaboration/health?from=&to=&metrics=` → `{range,metric_version,coverage_start,partial,computed_at,metrics,data_quality}`。每个指标包含单位、定义版本、值、来源和可钻取任务列表链接；无数据返回 0，数据不足返回 `null` 和原因。`GET .../health/tasks?metric=&from=&to=&limit=&cursor=` 返回该指标相关的已授权任务、计算依据和对象链接；按稳定键分页，必要时采用 P0 的共享短期快照。

数据尽量实时从事件计算；如使用 rollup，标注 `computed_at`、延迟及覆盖范围；重建可重复且结果一致。事件写入与状态变更事务相同，历史补录使用不同来源字段并可审计。默认不输出消息正文、用户名排行榜或外部通知；数据保留期、聚合粒度及导出由管理员配置，删除/保留策略必须与任务和审计政策一致。初始建议原始指标事件保留 180 天、日聚合 365 天，删除前需确认产品及合规要求，不作为已实施规则。

## 6. 互通 R14

### 发现与版本

`GET /api/v1/collaboration/capabilities` 返回 `{contract_version, server_version, capabilities, limits, auth_modes, mcp_transport, deprecations}`。能力条目标识 `name`、`version`、`status`（stable/experimental）及与仓库有关的权限要求；只广告**实际启用**的能力，不包含当前用户无权知道的私有仓信息。仓库具体能力通过 `GET /api/v1/repos/{owner}/{repo}/collaboration/capabilities` 查询并执行认证和仓库权限检查。首版 MCP stdio 通过现有 `tools/list` 广告实际工具，使用 MCP initialize 协议协商；本设计不要求额外自定义 MCP 协议方法。

契约采用 `major.minor`：新增可选字段、能力或可选枚举值递增 minor；删除字段、改变既有语义或增加必填字段需要新 major 或新端点。客户端忽略未知响应字段和未知非关键扩展枚举；未知会改变授权、终态或安全行为的值按 `unknown` fail closed，不默认成功。服务端不得要求客户端忽略未知**请求**字段：写请求遇到未识别字段应明确拒绝，避免拼写错误静默造成错误操作。旧客户端缺失新可选字段按文档默认值处理。

OpenAPI、MCP tool schema 和 `capabilities` 由同源 DTO 或契约测试防漂移；各语言示例优先调用公开 API，不要求共享 Rust 内部实现。版本废弃信息给出替代版本与最早移除时间；建议至少 90 天窗口，具体支持策略由项目决定。旧行为在承诺窗口内需回归测试。

### 接力与恢复

两种客户端按首版创建不同会话，在同一账号下读同一任务、消息、交接、P0 问题及工作包。新客户端不能仅凭旧 session ID 或展示名继承其 session secret、个人已读或身份；旧会话失效按 P0 离线接手规则。公开导入/导出若后续实现，只导出调用者对每个仓库有权限读取的记录，标注版本、来源和截断；默认不包含密钥、凭据、私人已读位置和未经授权数据。导入不自动覆盖现有记录或重放写操作；首批互通无需实现导入/导出。

MCP 工具的 schema、错误 `isError` 和 REST 的状态语义必须一致；工具返回标注不可信内容、分页信息和能力版本。环境缺少某项能力时客户端展示可恢复提示或使用文档化的旧版降级，不得静默声称成功。协议版本升级先验证现有客户端兼容，不能把应用契约版本当作 MCP 协议版本。

| ID | 任务 | 依赖和退出标准 |
|---|---|---|
| X00 | 收集真实跨仓与跨 harness 场景；复核首版、P0/P1 实际合并契约、权限缓存及基线 | 形成范围、实例环境、目标 SHA 和用户路径；无此验证不预设 P2 必须整体实施 |
| X01 | 契约清单、能力发现、版本策略与 REST/MCP 契约测试 | X00；可与 X02/X03 并行；兼容和非兼容规则可执行 |
| X02 | 单实例跨仓 group/link、双仓权限、稳定分页、删除/恢复 | X00；无需跨仓依赖图；M01–M05 通过 |
| X03 | 业务事件、指标定义、覆盖标注与单仓健康查询 | X00 + 对应首版/P0/P1 事件来源；M06–M09；先单仓再考虑聚合 |

## 8. 验收标准

| ID | 场景 | 通过标准 |
|---|---|---|
| M01 | 创建者有双仓权限，随后只读者只可见锚仓 | 对隐藏目标不暴露名称、ID、SHA、数量、错误或游标信息；锚仓正文的主动共享风险有提示 |
| M02 | 双仓链接并发更新，重试同键或异体 | 版本 CAS 和唯一约束成立；同体一个效果，异体 409；不产生跨仓半写入 |
| M03 | 分页中撤权/重新授权，目标重命名、删除和恢复 | 后续页逐项重验；只显示当前可见数据；已有快照不添加新授权项；重启分页可发现新可见内容 |
| M04 | 无权仓多于可见仓、分页边界、快照过期 | `has_more`、页长及计数仅由可见集合决定；过滤后继续扫描；过期明确恢复，隐藏数量不可推断 |
| M05 | Git 对象验证后被回收；多实例与三数据库 | 状态明确 unavailable，不切换 SHA；多实例分页可恢复；SQLite/PostgreSQL/MySQL 的权限与事务分别通过 |
| M06 | 已完成、持续阻塞、区间前开始、期间重新打开的任务 | blocked 交集时间、左/右删失及两个计数按定义正确；状态来源标记自报 |
| M07 | pending/accepted/cancelled 交接及问题等待 | 各状态分别统计；时间交集正确；不会把接受解释为工作完成 |
| M08 | 指标上线前任务、缺少状态事件、过期路径声明未知 | coverage/partial/unknown 正确；不把缺数据当零；不能编造历史 |
| M09 | 非管理员、无权仓、并发事件和重建 rollup | 权限过滤有效；业务与事件原子、重建可重复；不输出其他仓数据或 Agent 排名 |
| M10 | 旧客户端读新增字段、未知普通与安全关键枚举、未知写字段 | 可选响应兼容；未知安全状态 fail closed；写入未知字段明确拒绝；无静默错误 |
| M11 | 能力关闭/开启、MCP schema 与 REST 对照、旧版降级 | 只广告已启用功能；版本、schema、错误语义一致；不可用时不伪报成功 |
| M12 | 两种真实 harness/客户端、同账号、两个真实仓库，权限不同；一方断线后接力 | 可见范围和任务接续符合授权，secret 和旧会话水位不转移；记录 Git SHA、服务/客户端版本和证据，不用 mock 冒充 |

并发和权限撤销以 barrier/可控故障点验证；覆盖 SQLite、PostgreSQL、MySQL 及多实例。缺失真实数据库或客户端时标记待验证，不能以单元测试替代运行验收。

## 9. 待决事项

1. group 可见性是否应更严格地设为各关联仓权限的交集？本文选择逐链接过滤，锚仓正文由创建者负责共享范围。
2. 健康指标默认管理员可见还是允许仓库成员查看？明确保留期限、用户删除和导出政策后才能实施数据生命周期。
3. 兼容支持窗口、capabilities 的稳定命名、首批支持的客户端及老版本降级策略须结合实际发布节奏确定。
4. P2 按用户实际跨仓与互通需求触发；若 P0/P1 契约变动，先更新本设计，再开始迁移或 API 实施。
