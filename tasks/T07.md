# Task T07 - [#19] PR 头部漂移：旧票失效事件化 + 门禁阻断

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。

## Task Constraint

这是 #19 步骤 3 的**修正版**。原方案要求「门禁票数改查 `authorization_decisions`」，核实后判定**不做表切换**（理由见下），改为修一个更实质的漏洞。

### 为什么不做表切换

票源是 `pr_reviews` 表：`current_human_approver_ids`（`crates/rg-db/src/ops/pr_review_ops.rs`）用「每个 reviewer 取最新一条 → 只留 approve → 按 `commit_id == head_sha` 过滤」算出票数，且**计数与"谁批了"是同一条规则**（函数注释明写这个意图）。这套 latest / 撤销语义是正确的、被测试覆盖的。改成查 `authorization_decisions` 需要在 approve 时双写两表并同步 latest 语义，等于制造两个真相源。**新表留给 CI 环境审批、发布、scope 扩权用**，PR 评审保持自己的专用语义。

### 真正要修的问题（已核实）

| 事实 | 证据（`ecea2cc`） |
|---|---|
| `pr.head_sha` **只在创建时设置一次，没有任何刷新逻辑** | `crates/rg-core/src/pull_request/service.rs:168`（`create_pr` 内）；全仓检索无 `refresh_pr_head` / `sync_pr_head` / `update_pr_head` |
| 评审票的 commit 默认取 `pr.head_sha`（不是实时分支头） | `crates/rg-core/src/review/service.rs:86`：`commit_id.or_else(|| pr.head_sha.clone())` |
| 门禁按 `pr.head_sha` 过滤票 | `crates/rg-core/src/branch_protection/merge_gates.rs:302` |
| 分支前进了**只报警告、不阻断** | `crates/rg-core/src/pull_request/readiness.rs:236-245` 产 `HEAD_SHA_STALE`；`merge_gates.rs` 里**没有** `HEAD_SHA_STALE` 引用 |

后果：**批准的是旧代码，合并的是新代码，而票照算**。`HEAD_SHA_STALE` 只是一句警告。

## 要求

### 1. head 同步（新增，CAS）

新增 `crates/rg-core/src/pull_request/head_sync.rs`：

```
sync_pr_head_on_push(db, repo_id, branch_name, new_sha) -> HeadSyncOutcome
```

- 找到 `state = open` 且 `head_branch = branch_name` 的 PR（可能 0 或 1 条；若有多条同 head_branch 的 open PR，全部同步并在返回值里列出）
- 用 CAS 更新 `pr.head_sha`：`UPDATE ... WHERE id = ? AND head_sha = <旧值>`；影响 0 行说明别人先改了，**不要重试覆盖**，返回 `Raced`
- `head_sha` 为空（老数据）时允许直接设为新值
- 幂等：`new_sha` 与 stored 相同则返回 `Unchanged`，不写库、不产生事件

### 2. 旧票失效事件化（用上 T06 的新表）

当 head 真的从 A 变到 B 时：

- 调 `rg_db::ops::authorization_ops::expire_on_head_sha_change(db, repo_id, pr_id, old_sha, "head_sha_changed")`
- 语义：该 PR 上绑定旧 head 的 `authorization_requests` 全部置 `expired` + `state_reason = head_sha_changed`，**不删行**（T06 已实现，本任务只需正确调用并补测试）
- 票本身仍在 `pr_reviews`（不迁移），但因为 `commit_id` 不再等于新的 `head_sha`，`current_human_approver_ids` 自然不再计入 —— 这就是"失效"的实质

### 3. 门禁阻断 stale（行为变更，这是本任务的重点）

`crates/rg-core/src/branch_protection/merge_gates.rs`：当 stored `pr.head_sha` 与 head 分支实时 tip 不一致时，**拒绝合并**，返回稳定码 `HEAD_SHA_STALE`，message 说明「批准与 CI 是针对旧提交判定的，请先把 PR 头同步到分支最新提交」。

- 与 `readiness.rs` 已有的 `HEAD_SHA_STALE` 用**同一个 code**，不要另造。
- 同步顺序很重要：`sync_pr_head_on_push` 应该在 push 后立即跑，所以正常情况下不会触发阻断；阻断是**兜底**（同步失败、老数据、手工改库）。
- 这一条会让「分支前进后仍可合并」的现状变成「必须先重新批准」。这是**故意的行为变更**，必须逐条列出受影响的测试并改测试（**不许放宽实现**）。

### 4. push 侧接线（对 `rg-http/src/lib.rs` 只加一行）

在 `post_push_hooks` 里调用 `head_sync::sync_pr_head_on_push`（每个被推的 ref 一次）。**只加这一处调用**，不要重构周边。

⚠️ 同文件的路由注册段（`build_routes`）由并行任务 T08 独占，**严禁触碰**。你只改 `post_push_hooks` 函数体内。
