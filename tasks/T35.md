## 现状事实（需复核并量化）

| 项 | 现状 | 出处 |
|---|---|---|
| 实例数 | 单一 `ironforge` 服务，无副本 | `deploy/docker-compose.yml` |
| DB | SQLite 单文件（默认），可选 postgres/mysql（`db-postgres`/`db-mysql` feature） | `crates/rg-db/src/lib.rs` |
| 存储 | 本地文件（`/data/repos`、`/data/config`、`/data/logs`），S3 已实现（BlobStorage） | `Dockerfile`、`rg-core/src/blob_storage/` |
| 队列 | 进程内 background_jobs（持久表 + 原子 claim + 死信），**无 Redis**；index/archive 仍是进程内任务 | gap list 同条目 |
| 登录态 | JWT HS256（无服务端 session） | `rg-core/src/auth/jwt.rs` |
| 迁移 | 启动时自动跑（`ironforge migrate`），无版本门禁 | `rg-cli` |

## 要做的五件事

### 1. 单机部署的失效矩阵

列出所有失效模式，每行：**现象 / 数据影响 / 恢复动作 / 当前是否会自动恢复**。

至少覆盖：DB 文件损坏、DB 锁死（WAL 下写并发）、`/data/repos` 磁盘满、进程 OOM 被杀、宿主重启、S3 不可达、迁移中途失败、`reverse proxy` 与实例时钟不一致导致 JWT 失效。

**每一条都要有代码或配置证据**（例如「迁移中途失败」要看 `rg-cli` 的 migrate 是否包事务、失败后 `_sea_orm_migration_history` 处于什么状态）。

### 2. 备份与恢复演练（本任务的核心交付）

写一个**可执行的演练步骤**（`docs/plans/T35-drill-backup-restore.md`）：

- 备份什么：DB 文件（或 pg_dump）、`/data/repos`（裸仓库）、`/data/config`（密钥）、**以及三者的原子性关系**——单独备份 DB 但 repo 目录是旧的会发生什么？
- 一致性点：SQLite 用 `VACUUM INTO` 还是 `sqlite3 .backup`？在 WAL 模式下哪种安全？
- 恢复步骤：停服 → 恢复顺序（config 先还是 DB 先）→ 校验（怎么确认恢复成功，给出**具体命令与预期输出**）
- **实测**：在本机用 docker 起一个新实例，备份 → 删数据 → 恢复 → 验证；把实际耗时与遇到的问题写进文档
- 已知的半成品：`deploy/post-restore-quiesce.sql` 是干什么的？读完解释清楚并在演练里用上

### 3. 滚动升级设计（不改 deploy/）

- 单实例升级：停机窗口多长？迁移是否可回滚？`down` 窗口有几步？
- 双实例滚动：**先列出阻塞项**——SQLite 能否两实例共享（答案是不能，为什么）、`/data/repos` 本地盘如何共享、进程内 background_jobs 会不会双跑。每项给出**最小改造量**
- 版本对等期：新旧版本同时在线时，DB schema 与 API 的兼容窗口是几个版本？
- 给出「升级 checklist」（升级前 / 升级中 / 升级后 / 回滚触发条件）
