## Task Constraint

**先读 `ironforge-docs/ci/adr-0001-third-party-actions-execution.md` 全文再动手。** ADR-0001 状态是 `Accepted`（2026-07-14），执行位置与信任边界已经冻结，本任务不得重新讨论这些决策：

1. 第三方 Action 只能分配给声明 `actions-v1` 能力的**专用外部 Runner**，不得在 IronForge 服务进程/服务主机执行
2. 每个 Job 一个新临时容器 + 临时网络，Job 结束销毁
3. 第三方 Action 禁止宿主机模式；无 image 或无可匹配沙箱能力时 **fail closed**

**本任务的切分判断（协调者已定，不同意就先停下讨论）：**

第三方 Action 分三类，成本差一个数量级：

| `runs.using` | 执行需求 | 本轮是否做 |
|---|---|---|
| `composite` | **纯 YAML 展开**，零新运行时 | ✅ **本轮做**——这是本任务的唯一实现目标 |
| `node*`（node16/node20/node24） | 需 Node 运行时 + 脚本执行沙箱 | ❌ 继续 fail closed，报错说明「需 actions-v1 runner（未实现）」 |
| `docker` | 需容器构建 + 运行 | ❌ 同上 |

理由：composite action 展开是**纯转换层工作**，不触碰执行沙箱，符合 ADR 的 fail-closed 边界，且能覆盖真实场景中相当一部分 Action（`actions/cache` 之外的多数自研 action 是 composite）。先把这层做好，比半成品沙箱有用。

## 现状事实

- `crates/rg-ci/src/gitea_actions.rs`：目前把多个 step 拼接成单个 `JobConfig.script`，丢失 step 生命周期、outputs、`pre/main/post`、运行时条件
- 内置适配只有 `actions/checkout`、`actions/cache`；其余 `uses:` 在创建 Pipeline 时**显式拒绝**（不静默忽略——这个行为要保持）
- `crates/rg-ci/src/runner.rs` 的 Docker Job 只有 `--rm` + 工作区挂载

## 要做的五件事

### 1. 读代码，确认拒绝路径

定位 `gitea_actions.rs` 里对 `uses:` 的判定与拒绝点，把实际代码行（`sed -n` 打印）贴进 plan 文档。确认：
- 拒绝发生在**创建 Pipeline 时**还是执行时
- 错误信息长什么样（用户看到的字）
- `uses` 的解析是否已处理 `owner/repo@ref`、`./local/path`、`docker://image`

### 2. Action 仓库获取

新增 `crates/rg-ci/src/action_fetch.rs`（或并入 `gitea_actions.rs`，你判断）：

- `owner/repo@ref` → clone 到缓存目录（`{workdir}/.ironforge/actions/{owner}/{repo}/{ref}/`）
- 缓存命中判据：目录存在 + 有 `action.yml` 或 `action.yaml`
- 支持 `owner/repo/subdir@ref`
- `./local/path` → 直接读工作区内路径，不 clone
- `docker://` → 直接返回「不支持」，走 fail closed
- 网络失败/ref 不存在：错误必须能区分「网络问题」和「ref 不存在」

### 3. `action.yml` 解析与 composite 展开

```rust
pub enum ActionRuns {
    Composite { steps: Vec<ActionStep> },
    Node { using: String },     // 不展开
    Docker { image: String },   // 不展开
}
```

展开规则：
- `inputs` → 以 `${{ inputs.x }}` / `${{ github.action_path }}` 替换进 step 的 `run` 与 `env`
- `runs.steps[].uses` **递归展开**（composite 可嵌套），**深度上限 5，超出 fail closed**
- 循环引用检测（A→B→A）必须 fail closed
- `outputs` 映射：composite 的 `outputs.x.value` 要写进父 step 的 outputs
- 展开后产生的 step 与原有 step 排在同一个 Job 里，保持顺序

### 4. 能力协商

- Runner 注册/心跳上报能力集合，`actions-v1` 为其中一个值（先读 `rg-runner/src/main.rs` 与 `rg-http/src/api/runners.rs` 确认现有能力上报机制，**能复用就复用，不要新造**）
- Pipeline 调度时：含 composite 展开后的 step **不需要** `actions-v1`（它已变成普通 step）；含 node/docker action 时必须匹配 `actions-v1`，否则在**创建 Pipeline 时**拒绝并给出明确错误
- 保留现有「未知 uses 显式拒绝」的语义——只是拒绝时机与文案要更准确

### 5. 测试

必须覆盖（写在 `crates/rg-ci/tests/`）：

1. 单层 composite 展开：2 个 step → 展开后 step 数正确、顺序正确
2. 嵌套 composite（2 层）展开正确
3. 循环引用 → 报错且不是 panic
4. 深度超限（6 层）→ 报错
5. `node20` action → 拒绝路径，错误含 `actions-v1`
6. `./local/path` 形式的 composite → 展开正确
7. `inputs` 替换：默认值 + 调用方覆盖两种情况
8. 现有 `actions/checkout`、`actions/cache` 行为不变（回归）

用**本地 fixture 目录**放假的 `action.yml`，不要依赖网络。真实网络获取单独写一个 `#[ignore]` 测试。
