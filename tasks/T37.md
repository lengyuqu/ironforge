# Task T37 - 增量 fetch 的对象级差集（实测放大 ~8000×）

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。
> 来源：T32 性能基线实测（`docs/plans/T32-baseline-report.md` §瓶颈 1）。

## Task Constraint

**现状：客户端只缺 8 个对象，服务端发 20,224 个。**

T32 在 medium 数据集（2,000 commits / 20,000 files）上实测，改 1 个文件后 `git fetch`：

| 指标 | 服务端实际生成 | 客户端真实缺的 | 放大 |
|---|---|---|---|
| pack 字节 | 50,066,689 B | 5,973 B | **≈8,380×** |
| 对象数 | 20,224 | 8 | **≈2,528×** |

large 数据集（20,000 commits / 200,000 files）更极端：992,218,757 B / 201,112 对象，真实增量 11,240 B（**≈88,270×**）。

这不是"慢一点"，是**每次日常 `git pull` 都在传输整个工作树**。20,224 这个数字正好等于 medium 的 20,000 文件数，这就是根因的线索。

## 根因（已核对代码，不要从别的前提出发）

`crates/rg-git/src/ops.rs`：

1. `pack_for_wants_filtered`（`:1116`）**确实**按 haves 剪枝了 commit 遍历——`:1173` 附近 `walk.with_hidden(hidden)`，`hidden` 来自 `peel_list(haves)?`。所以 **commit 层是对的**。
2. 漏的是**对象层**：`:968` `input_object_expansion: ObjectExpansion::TreeContents`。

`TreeContents` 的语义（`gix-pack-0.77.0/src/data/output/count/objects/types.rs:41-46`）：对每个 input commit，展开它的**完整 tree**——所有嵌套 tree 和全部 blob。

于是：即使 haves 只留下 1 个待打包 commit，也会把这 1 个 commit 的整个工作树全部塞进 pack。

**结论：commit 已剪枝，缺的是"对象相对客户端已有内容做差"。**

## 硬约束

1. **不得改协议线格式。** pack 的内容变、大小变，但 `upload-pack` / `receive-pack` 的协商与 sideband 行为不得变。客户端必须无感。
2. **不得影响首次 clone。** 无 haves（或 haves 为空）时必须仍发全量对象。`shallow_mode` 下同理（`ops.rs:1163-1170` 的注释：deepening with empty boundary == full unshallow，此时**不能**按 haves 剪）。
3. **不得影响 partial-clone `filter`。** `requested` 集合（直接 want 的 blob/tree）与 `ObjectFilter`（blob:none 等）逻辑必须保持——filter 是"客户端只要一部分"，差集是"只发客户端缺的"，两者正交。
4. **不得改 `Cargo.toml` / `Cargo.lock`。** gix 0.84 现成 API 够用（下面给了依据）。
5. **只碰 `crates/rg-git/`。** 不改 rg-http / rg-core / rg-ci / 迁移 / 路由。
6. **不得顺手做 T38。** pack 流式化（`send_packfile` 的 `read_to_end` → 1.21 GB 驻留）是独立任务，同文件串行，本任务只做差集。

## 关键 API 事实（已查源码，省你一轮）

`ObjectExpansion` 有三个值（`types.rs:37-54`）：

- `AsIs` —— 只把 input 本身入 pack
- `TreeContents` —— 当前用的，展开完整 tree
- `TreeAdditionsComparedToAncestor` —— 文档说 "finally obtain the added/changed objects when comparing the ancestor trees with the current tree" / "useful to build a pack containing only new objects compared to a previous state"

**`TreeAdditionsComparedToAncestor` 看着正好，但它会自己走祖先链**（"obtain its ancestors and turn them into pack entries"）。我们的 input 已经被 haves 剪枝过，这个模式会重新引入已剪枝的祖先 commit ⇒ 对大历史会退化。**直接换它大概率不达标，先做小实验验证再决定。**

## 技术路线（按优先级试，前一步不达标再走下一步）

### 路线 A：每个待打包 commit 与自己的第一父做 tree diff

对一个待打包的 commit C：

- 若 C 的父 P 已存在于客户端（P ∈ haves 或 P ∈ hidden 集合）→ 只发 `diff(P.tree, C.tree)` 得到的 tree/blob，加上 C 本身
- 若 C 是 root commit（无父）→ 发全量 tree（这是正确行为，客户端确实什么都没有）
- 若 C 是 merge（多父）→ 对**每个**父比对，取并集（任一父缺失的对象都要发；最保守的正确做法是并集，不要只取第一父）

对 medium 改 1 文件的场景，haves 剪枝后剩 1 个 commit，它与父只差 1 个 blob ⇒ 对象数应降到个位数。

### 路线 B：`TreeAdditionsComparedToAncestor` + input 收窄

若路线 A 在 gix 里不好实现（例如没有稳定的 tree-diff-into-object-ids 入口），试路线 B：给 `count::objects` 的 input 只放"需要打包的 tips"，让该模式自己算差。**但要实测对象数**——它走全祖先，很可能不达标。达标才用。

### 路线 C：直接调 `git pack-objects --revs`

**不推荐**，且与本项目"消除 git CLI"的方向冲突。只有在 A/B 都不可行时才考虑，且必须走 `GitCommandGateway` 并在任务卡记录为什么 gix 做不到。

## 必须处理的边界

1. **`requested` 里的裸 blob/tree**（partial clone 惰性取对象）：这些是直接 want 的，必须原样入 pack，不参与差集计算。
2. **`shallow_boundaries` 非空**：boundary commit 的 tree 必须全量展开（`ops.rs:1188-1193` 现有逻辑），因为 shallow 客户端拥有 boundary commit 但不拥有它的 tree。改差集时不要破坏这条。
3. **filter 与差集叠加**：先算差集，再按 filter 筛（`ops.rs:973-980` 的 `counts.retain`），顺序不能反。
4. **空 haves**：全量，不得退化成空 pack。

## 验收（全部必须满足）

### 一、量化指标（复用 T32 的 `crates/rg-git/tests/perf_fixture.rs` 数据集）

| 场景 | 现状（T32 实测） | 通过线 |
|---|---|---|
| medium 改 1 文件 fetch | 20,224 对象 / 50,066,689 B | **≤ 100 对象 / ≤ 200 KB** |
| large 改 1 文件 fetch | 201,112 对象 / 992,218,757 B | **≤ 100 对象 / ≤ 1 MB** |
| small 首次 clone | 182.6 ms | 不劣化 > 20% |
| medium 首次 clone | 3,129.6 ms | 不劣化 > 20% |
| medium 首推 | 3,949.5 ms | 不劣化 > 20% |

首次 clone / 首推的数字必须实测给出，不许推算。

### 二、内容正确性（**最重要，不能只验对象数**）

**对象少了但内容错了，是本任务最坏的结果。** 必须验证：

1. **真实 git 客户端**跑 `git clone` → 改文件 → `git commit` → `git push` → 另一侧 `git fetch` + `git pull`，工作树文件内容逐字节一致
2. `git fsck --strict` 在 fetch 侧通过
3. 跨 commit 的**删除**（不是修改）也要覆盖：删除一个文件后 fetch，客户端必须收到"删除"而不是保留旧文件
4. **重命名**：`git mv` 后 fetch，客户端结果正确
5. 用 `git verify-pack -v` 或 `git cat-file --batch-check --batch-all-objects` 对比 fetch 后两侧对象集合，缺任何一个客户端需要的对象即为失败

### 三、回归

`cargo test -p rg-git` 全绿；T32 的 5 个测量点不留回归。

## 风险提示

- **`gix` 的 tree diff 入口需要自己找。** 若 `gix` 没有"给两个 tree 返回差异对象 id 列表"的稳定 API，允许自己 walk tree（`repo.find_object(tree_id)?.into_tree()` 递归比对 entry name + oid），这比等 gix 更实际。walk 时要处理子模块（`EntryMode::Commit`）和符号链接。
- **merge commit 的并集可能超预期。** 若某个 merge 的多个父都不在 haves 里，差集会退化成接近全量——这是**正确**的（客户端确实缺），不要为了数字好看去砍。
- 先做小实验确认路线，再动 `ops.rs`。不要在没验证 API 行为的情况下改主路径。
