## Task Constraint

**现状：一次 large 仓库 clone，服务端常驻 1.21 GB。**

T32 实测（20,000 commits / 200,000 files）：pack 1,828 MiB 磁盘、clone 时单个 `Vec<u8>` 驻留 1.21 GB。这与项目定位直接冲突——`deploy/README.md` 按「单机小团队、内存 <50 MB 量级」设计。

更要紧的是：**并发两三个 clone 就 OOM**，而 OOM 是整进程崩溃，会带走所有在线用户的连接（`panic = "abort"`，无 unwind）。

## 根因（已定位到行，不要从别处找）

### 主因：pack 生成写进 `Vec<u8>`

`crates/rg-git/src/ops.rs:1095-1105`：

```rust
let mut pack = Vec::new();                  // ← 1.21 GB 在这里
let mut writer = output::bytes::FromEntriesIter::new(
    in_order,
    &mut pack,                              // ← W = &mut Vec<u8>
    num_entries,
    ...
);
```

`FromEntriesIter<I, W>` 的 `W: std::io::Write`（`gix-pack-0.77.0/src/data/output/bytes.rs:33-37`）——**gix 本来就支持写往任意 Writer**，我们选了 `Vec`。

### 次因：HTTP 层再把响应整体读进第二个 `Vec`

`crates/rg-http/src/lib.rs` 三处同构：

```rust
let (buf_reader, mut buf_writer) = tokio::io::duplex(64 * 1024);
let reader_task = tokio::spawn(async move {
    let mut output = Vec::new();
    let _ = buf_reader.read_to_end(&mut output).await;   // ← 又一个 Vec
    output
});
```

- `:2983` V2 POST
- `:3038` V1 upload-pack（`handle_upload_pack_http`）
- `:3210` V1 receive-pack

`duplex(64KB)` 存在的意义是防死锁，但读端被用来**收集**而不是**转发**，缓冲就白设了。

## 只改 upload-pack，不改 receive-pack

- **upload-pack 响应 = pack（大）** → 流式收益 100%
- **receive-pack 响应 = report-status（小）** → 流式收益接近 0，但改动风险高（要先读客户端 pack、index、跑 branch protection、更新 refs，才知道成败；流式化会让"失败改状态码"变成不可能）

`receive-pack` 那处 `read_to_end` **保留**，只加注释说明为什么不做。

## 硬约束

1. **不改 `Cargo.toml` / `Cargo.lock`。** `tokio-util 0.7` 已带 `io` feature 在 `crates/rg-http/Cargo.toml:39`，`SyncIoBridge` 可用。
2. **不改协议线格式。** 字节流完全相同，只是不再先攒成 Vec。客户端必须无感。
3. **`pack_for_wants` 等现有公开签名不要直接改**（`pack_for_wants` / `pack_for_wants_opts` / `pack_for_wants_filtered` 被 `pack_universe`、`fork_repo`、多处测试使用）。新增 `_into` 变体，让旧签名变成 `_into` 的薄包装（`generate_pack_into(..., Vec::new())`）。
4. **不改 `rg-core` / `rg-ci` / 迁移 / 路由。**
5. **错误语义必须明确**（见下）。

## 最大的技术风险：流式化之后，无法在发出响应头前知道成败

这是本任务唯一容易做错的地方，先想清楚再写代码。

HTTP 的语义是：headers 一旦发出，状态码就定了。当前实现是"先收集完 → 知道成败 → 再决定 200 还是 500"。

流式化后：
- **pack 生成期出错**（对象库损坏、磁盘读失败）→ headers 可能已经发出（`200 OK`），只能在流中途断掉
- 客户端会看到 "early EOF" / "fatal: the remote end hung up unexpectedly"

判断：**这个代价可接受**，但要满足两条：
1. **协商阶段的所有可能失败必须发生在流开始之前**（wants 解析、haves 解析、filter 校验、shallow 边界、ref 解析）。这些已经在生成 pack 之前做完了——确认这一点，不要把校验挪到生成之后。
2. 失败时必须 `tracing::error!` 记下真实原因（客户端只会看到断流，日志是唯一线索）。

不要试图"先生成到临时文件，成功了再流出去"——那只是把内存压力换成磁盘，large 仓库要多写 1.8 GB，且延迟翻倍。**直接流，接受 early EOF。**

## 实现路径

### 第一步：rg-git 侧泛型化

`ops.rs`：

```rust
// 新增，公开
pub fn pack_for_wants_into<W: std::io::Write>(
    repo_path: &Path, wants: &[String], haves: &[String],
    shallow_boundaries: &[String], out: W,
) -> anyhow::Result<W>;

// 同理 filtered 版本（带 filter 与 shallow_mode）
pub fn pack_for_wants_filtered_into<W: std::io::Write>(..., out: W) -> anyhow::Result<W>;
```

内部：`generate_pack_with` / `generate_pack_filtered_with_tips` 也泛型化，`FromEntriesIter::new(in_order, out, ...)` 直接传下去，`writer.into_write()` 拿回 `W`。

旧的 `pack_for_wants` 保持签名，实现改为：
```rust
let mut buf = Vec::new();
pack_for_wants_into(repo_path, wants, haves, shallow, &mut buf)?;
Ok(buf)
```

`pack_universe` 同理（它走 `generate_pack_with`）。

### 第二步：rg-http 侧流式 body

`crates/rg-http/src/lib.rs` 的 V1 upload-pack 与 V2 POST 两处。

要点：

1. **不要用 `duplex` 收，直接把读端包成 body。** axum 0.8 支持 `Body::from_stream(stream)`，把 `tokio::io::AsyncRead` 转成 `Stream` 需要用 `tokio_util::io::ReaderStream`（`tokio-util` 的 `io` feature 已开，确认 `ReaderStream` 可用；不可用则手写一个 4 行 `poll_read` 转 `Stream` 的适配器）。

2. **pack 生成必须在 `spawn_blocking` 里跑**，否则 CPU 密集的 pack 生成会占死 async worker。当前代码是在 async 上下文里直接调 `pack_for_wants`，本身就是问题——顺手修掉。

3. **同步 Write 桥接异步 Write**：`tokio_util::io::SyncIoBridge::new(async_writer)` 得到 `impl Write`，在 `spawn_blocking` 内使用。**注意 `SyncIoBridge` 必须在 blocking 线程里用**（它的文档明确说了：调用方负责保证不在 async 上下文），`spawn_blocking` 正好满足。

4. **背压靠有界 channel**：`duplex(64 * 1024)` 本身就是有界的（容量 64 KB），写满即阻塞写入方 → 天然背压。**不要**换成 `mpsc::unbounded_channel`，那会把内存问题原样搬回来。

5. **超时**：现有 `git_stream_timeout()` 包的是整个 handler。流式化后 body 传输在 handler 之外继续，超时语义会变。要么把超时放在 stream 上（`tokio::time::timeout` 包每次 `next()` 不现实），要么明确记录"超时只管到 body 开始"。**选后者并写进文档**——不要假装超时还覆盖全程。

### 第三步：测量

用 `/usr/bin/time -l` 或后台 `ps -o rss=` 采样峰值 RSS。必须给出**同一数据集、同一 profile** 的前后对比。

- receive-pack 流式化（响应小，风险高）
- 并发 pack 数量上限 / 限流（另一件事，属运维层）

## 风险提示

- **先确认协商期的失败全部早于流出**。把 `upload_pack.rs` 里生成 pack 之前的所有校验列一遍，确认没有"生成到一半才发现要报错"的路径。
- **`spawn_blocking` 的返回要接住**。当前是同步调用，改成 spawn 后如果 `JoinHandle` 丢了，panic 会被吞，客户端只看到断流。必须 `let _ = handle.await` 并检查 `JoinError`。
- **`ReaderStream` 与 `duplex` 的所有权**：读端给 body，写端给 `SyncIoBridge`，两个所有权都要正确 move 进各自任务，否则编译不过或死锁。
- 测 RSS 时注意 `cargo test` 的进程不等于被测进程，要在被测 binary 上测（起服务再 clone）。
