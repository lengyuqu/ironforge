# Task T16 - [#15 第四步] `pull_request.merged` 走事务内事件写入（端到端验证）

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。

## Task Constraint

T13 打通了机制、T14/T15 放宽了签名，但**只有 `issue.opened` 一条链路真正在事务内写事件**。本任务做第二条，且换成更高价值的 `pull_request.merged`——它是 #15 分析里点名的典型案例（注释明写 "outside the transaction on purpose"）。

**为什么不是 CI 路径**：13 个 `trigger_*` 事件助手里**没有** pipeline/job 相关事件（只有 release / branch / tag / issue / PR / milestone），CI 写路径搬进事务没有可投递的事件，做了也不验证任何东西。

## 现状（`6d32865` 时点，已逐行确认）

`crates/rg-core/src/pull_request/service.rs` 的 merge 路径：

```rust
let txn = db.begin().await.context("db: begin PR merge transaction")?;
let merged_pr = pull_request_ops::update(&txn, active).await?;
rg_db::ops::pr_event_ops::record(&txn, ..., "pull_request_merged", ...).await?;   // PR 自己的事件表
txn.commit().await.context("db: commit PR merge transaction")?;

// Trigger pull_request.merged webhook (outside the transaction on purpose)
let merge_payload = serde_json::json!({
    "id": merged_pr.id, "repo_id": ..., "number": ..., "title": ...,
    "merge_commit_sha": merge_commit_sha, "strategy": ...,
});
if let Err(e) = crate::webhook::service::trigger_pr_merged(db, merged_pr.repo_id, &merge_payload).await {
    tracing::warn!("Failed to trigger PR merged webhook: {e}");   // ← 失败只 warn
}
```

`trigger_pr_merged`（`webhook/service.rs:912`）只做包装：
```rust
let payload = json!({ "event": "pull_request.merged", "pull_request": pr });
trigger_event(db, repo_id, "pull_request.merged", &payload)
```

注意：`pr_events` 的写入**已经在事务内**了（那是 PR 自己的表）。本任务要搬的是 `repo_events` + webhook 这一段。

## 要求

### 1. 改成「事务内记录 + commit 后投递」

```rust
let txn = db.begin().await.context("db: begin PR merge transaction")?;
let merged_pr = pull_request_ops::update(&txn, active).await?;
rg_db::ops::pr_event_ops::record(&txn, ...).await?;

// 新增：payload 在事务内构造（merged_pr 是 update(&txn) 的返回值，事务内可用）
let merge_payload = serde_json::json!({ ... });   // 字段与现在逐字节一致
let merge_event_payload = serde_json::json!({
    "event": "pull_request.merged",
    "pull_request": merge_payload,
});
crate::webhook::service::record_event_in_txn(&txn, merged_pr.repo_id, "pull_request.merged", &merge_event_payload).await?;

txn.commit().await.context("db: commit PR merge transaction")?;

// 投递（不写日志）
if let Err(e) = crate::webhook::service::deliver_event(&db, merged_pr.repo_id, "pull_request.merged", &merge_event_payload).await {
    tracing::warn!("Failed to deliver PR merged webhook: {e}");
}
```

要点：
- **payload 逐字节等价**：`merge_payload` 的字段集合、顺序、值都不许变；外层必须是 `{ event, pull_request }` 两键（与 `trigger_pr_merged` 一致）。
- `record_event_in_txn` 失败 → 用 `?` **回滚整个 merge**（与 T13 对 `issue.opened` 的处理一致：宁可 merge 失败，不要「merge 成功但事件丢失」）。
- `deliver_event` 失败 → 只 warn，不影响 merge 结果（与现有行为一致）。
- 不要动 `pr_event_ops::record` 那一行（PR 自己的事件表，本来就在事务内）。

### 2. `trigger_pr_merged` 怎么处理

它现在**没有别的调用点**（只有这里）。两种选择，自己判断并在 plan 里说明理由：

- **A：保留**，加注释说明「仅用于不参与 merge 事务的场景」，或
- **B：删除**（如果确认无调用点），避免以后有人误用退回旧缺陷

T13 留下了同类隐患（`trigger_issue_opened` 已无调用点但保留），plan 里请提一句是否该一并清理。

### 3. 验证

1. **正常 merge**：`repo_events` 里 `pull_request.merged` **恰 1 行**（不是 2 行），webhook receiver 收到 1 次，payload 的 `data.event` / `data.pull_request.*` 与 merge 结果一致。
2. **不重复写**：明确断言只有 1 行（`deliver_event` 不再写日志这条必须钉住）。
3. **回滚不写事件**：merge 事务失败时 `repo_events` 无该事件。**如果 merge 失败点都在事务之前**（保护规则、冲突检查等），构造不出「事务中途失败」的场景，那就**如实说明**「本路径的失败点均在事务前，无法构造中途回滚，故此项由 T13 的机制测试覆盖」，不要为了凑测试写假场景。
4. **既有 merge 测试全绿**（`rg-core` 里所有 PR merge 相关测试）。
