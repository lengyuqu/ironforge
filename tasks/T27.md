### 1. 规模实测（必须用真实数据，不要拍脑袋）

在 **IronForge 仓库自身**上跑一遍现有 `extract_outline`，统计：

| 指标 | 说明 |
|---|---|
| 参与索引的文件数 | 按 `supports()` 过滤后 |
| 总定义数（`OutlineItem` 数） | 含 children 递归 |
| **总标识符出现数**（引用侧） | 这是表规模的主要来源，必须实测，不要用"每文件数百"的估计 |
| 单文件最大值 / 中位数 | 看长尾 |
| 按语言分布 | 五语言各自的量 |

**怎么做**：写一个临时脚本或用 `cargo test` 里的一次性统计（`#[ignore]` 的测试也行），遍历仓库跑 `extract_outline`，输出上表。脚本**不要提交**（或用 `#[ignore]` 测试形式提交，自己判断哪个更合适并在 plan 说明）。

如果实测发现「每文件标识符数」远低于或远高于 #63 原文的"数百"，**明确指出来**——原文那句话是估计，实测才有决策价值。

### 2. 规模推算（三种仓库尺寸）

| 仓库尺寸 | 文件数 | 估算行数（定义 + 引用） | 估算磁盘 |
|---|---|---|---|
| 小（本仓，~1k 文件） | 实测 | 实测 × 系数 | — |
| 中（~10k 文件） | ×10 | | |
| 大（~50k 文件，monorepo） | ×50 | | |

磁盘估算：每行约 100-150 字节（含索引）。给出计算过程，不要只给结论。

### 3. 保留策略（给选项 + 明确建议）

必须回答：
- **留哪些 commit**？候选：只留默认分支 HEAD / 最近 N 个 commit / 每个被索引的 branch 各留 HEAD / 按 LRU
- **N 取多少**？依据是什么（查询需求 vs 磁盘）
- **什么时候清**？复用现有清理任务的注册方式（T11 的 `agent_draft` 清理、T19 的 outbox sweep 都是先例）
- **清理的判据**：按 `commit_sha` 不在保留集 / 按 `created_at` 超期 / 两者结合

**必须给出建议方案 + 理由**，不要罗列选项完事。我倾向「默认分支 HEAD + 最近 N 个 commit（N 由磁盘预算反推）」，但你要用实测数据验证这个方向是否成立。

### 4. 表结构草案

```sql
-- 草案，不必最终定稿
symbol_definitions(id, repo_id, commit_sha, path, name, kind, start_line, end_line)
symbol_references(id, repo_id, commit_sha, path, line, name, context)
```

要说明：
- 索引怎么建（`(repo_id, commit_sha, name)` 是查定义的主路径）
- `name` 是否要规范化（大小写？`::` 分隔？）
- 是否要存 `signature`（体积 vs 有用性）

### 5. 诚实边界（照抄 #63，落到具体字段）

#63 列的四语言限制必须进文档，并说明如何在数据模型上表达：

- Rust：宏展开、`dyn Trait` 动态分发、`impl Trait for X` 的方法调用（tree-sitter 做不到类型推断）
- TS/JS：`obj[key]` 动态属性、`any` 传播
- Python：`getattr`、猴子补丁
- Go：接口方法集运行期确定，静态只能按名匹配（**会误报**）

**必须体现在输出契约上**：`confidence: exact | name_match`，不能假装都是精确的。
