# Task T20 - [#19·步骤6] `scope_expand` 执行面：repo 系列内提权

## Task Constraint

#19 的步骤 1-5 已完成（表 + 状态机 + CI 环境审批接入 + 合并侧接入 + capability 注册 + 通知面）。**只剩步骤 6**：#19 原文说「`scope_expand` 最后做 —— 它是唯一没有现成执行面的 action，先定义清楚『扩权后 agent 到底拿到什么』，否则做出一个批了没用的按钮。」

**本任务就是回答那个问题并实现它。**

### 答案（本任务的定义）

**扩权 = 在 `repo` 系列内提权，执行面是原地更新 `api_tokens.scopes`，不重新签发 token。**

- agent token 的 scope 被 `agent::validate_agent_token_scopes` 限制在 `repo` / `repo:write` / `repo:collab` / `repo:read` 之内，**不接受 `user`/`admin`**。所以 `scope_expand` 不可能、也不允许越过这条线。
- 典型场景：agent 拿 `repo:read` token 做探索，需要推代码时申请扩到 `repo:write`，人批准后**同一个 token 立即生效**（不需要换 token、不需要重启会话）。
- 绑定对象：`subject = token_id`，参数 `{"target_scopes": "repo:write"}`。

### 已核实的现状（`8ee297d`）

- `Action::ScopeExpand` 已在 `action.rs:27` 定义（注释写着 "Not implemented in step 1"）。
- `evaluator.rs:210` 对 `ScopeExpand` 返回 `501 AUTHORIZATION_ACTION_NOT_IMPLEMENTED`。
- 测试 `mod.rs:596 scope_expand_is_not_evaluated_yet` 断言了这个 501 —— **本任务要让这条测试变成相反的断言**（能被求值），不是删掉它。
- `consume`（`mod.rs:313`）**是通用的**：只做 pending / 过期 / 票数 / CAS 四件事，**不分发 action**。执行面在调用方的事务里。
- token 存在 `api_tokens`（`scopes` 字段 + `repo_allowlist`），创建入口在 `rg-http/src/api/users.rs:600`。

## 要求

### 1. evaluator：给 `ScopeExpand` 一条真实规则

不能沿用其它 action 的规则抄。`scope_expand` 的语义是「扩大 agent 能做什么」，所以：

- 谁能批：**repo 的管理员**（`writers: false`、`collaborators: false`、`admins: true`），`required_approvals: 1`。
  理由：扩权影响的是整个仓库的写能力，不该由 collaborator 自批。**如果你认为应该更严（比如要求 owner），在 plan 里说明并自己定，但要写清理由。**
- **申请人 ≠ 批准人**这条要在这个 action 上生效（沿用现有 `authorization_decisions` 的唯一键 + 自批守卫）。
- `expires_at`：原方案说 scope 扩权 7 天（其它 action 30 分钟）。照此实现，并在 plan 说明为什么 scope 需要更长。
- **`subject` 校验**：必须是数字 token id。非数字 → `invalid_input`（参考 `ProtectedBranchMerge` 对非数字 subject 的处理）。

### 2. 新执行面 `crates/rg-core/src/authorization/scope_expand.rs`

```rust
/// 消费一张 scope_expand 票据：把 token 的 scope 原地提升到 target。
/// 业务写与 consume 必须在同一事务。
pub async fn consume_scope_expand(
    db: &DatabaseConnection,
    request_id: i64,
    actor_id: i64,          // 批准人 / 执行人
    token_id: i64,
    target_scopes: &str,
) -> CoreResult<TokenScopeExpandResult>
```

事务内顺序：

1. `begin`
2. 读 request，校验 `action == ScopeExpand`、`subject == token_id.to_string()`（不一致 → `invalid_input`，不要静默用请求里的）
3. **校验目标是扩大而非收缩/平移**：必须能证明 `target` 覆盖 `current` 的全部权限。`pat_scope` 里已有层级判定（注意：反向清单里记过 `has_scope` 的层级曾漏 `repo:collab → repo:write`，**先去核实现在的实现**，别照抄假设）。判定不出来就停下报告，不要用「字符串不相等」糊弄。
4. **校验 `target_scopes` 通过 `validate_agent_token_scopes`**（不能借扩权拿到 `user`/`admin`）
5. 更新 `api_tokens.scopes = target_scopes`（`update` + `updated_at`）
6. `consume(&txn, request_id, actor_id, effect_hash)` —— `effect_hash` 用能唯一标识结果的值（如 `sha256(f"{token_id}:{target_scopes}:{request_id}")`，具体格式自己定，plan 说明）
7. `commit`

返回 `TokenScopeExpandResult { token_id, previous_scopes, scopes }` 便于调用方/审计。

**失败处理**：任何一步失败 → 整个事务回滚，票据保持 `pending`（`scope_expand` 可重试）。这与现有 `consume` 的语义一致。

### 3. 端点

如果 `consume` 已有 HTTP 端点（`POST /api/v1/authorization/{id}/consume` 或类似），**不要新开一条**——扩展现有端点让它接受 `scope_expand` 的 body（`token_id` + `target_scopes`），或在 handler 里按 `request.action` 分发到 `consume_scope_expand`。

先读现有 handler 再决定。**如果现有端点的 body 结构无法容纳新参数，停下报告**，不要为此破坏已有契约。

### 4. 申请侧

agent 如何发起 `scope_expand` 申请？如果现有 `POST /authorization` 已经能传任意 `action` + `subject` + parameters，那么**不改代码**，只在测试里验证 agent 能申请、且不能批准。如果它硬编码了允许的 action 列表，把 `scope_expand` 加进去。

### 5. 测试（每条都要真断言）

1. **evaluator 能求值**：`evaluate(db, repo, Action::ScopeExpand, "1")` 返回规则而非 501（改掉 `scope_expand_is_not_evaluated_yet`）
2. **非数字 subject 被拒**
3. **`user`/`admin` 目标被拒**（借扩权越权）
4. **收缩被拒**：`current = repo:write`，`target = repo:read` → 拒绝
5. **正常扩权**：`repo:read → repo:write`，token 的 `scopes` 真的变了，`consumed_at` 被写入，票据不能再消费
6. **票数与状态**：未批准 → 409；已消费 → 409
7. **agent 不能批准**：`requested_by_kind = agent_session` 的 actor 调批准 → 403
8. **target 与 subject 不匹配**：request.subject 是 token A、传入 token B → 拒绝
9. **事务性**：更新 token 后若 consume 失败（票已被并发消费），token 的 scopes **必须回滚**。这条是死线，用并发或注入验证。
