## Task Constraint

只做 R3 的 **P1（信封与头 + 5xx 重试）**，**不做** P2 事务内写入、P3 outbox。三阶段拆分见 `ironforge-docs/architecture/agent-principals-design-and-roadmap-2026-11.md` §5.1 R3。

已核实锚点（以 `0523bb2` 为准，行号会漂）：

- `crates/rg-core/src/webhook/service.rs`：`trigger_event`（约 :131）、`deliver`（约 :257）、签名头 `X-Hub-Signature-256`（约 :295）、`deliver_retry_job`（约 :308）。
- 现状：15 个事件各拼 `json!`，无统一信封、无 schema 版本、无事件头；接收方 **5xx 被当成功**（只有传输错误入队重试）。
- `repo_events` 单写点在 `webhook/service.rs`（约 :227），读端 `crates/rg-http/src/api/repo_events.rs`（约 :113）。
- WebSocket 在 `crates/rg-http/src/ws.rs`（约 :196 / :345）。

**要求**：

1. 引入 `EventEnvelope { schema: 1, id: Uuid, kind, at, repo_id, actor: ActorRef, data }`（`ActorRef` 复用 `rg_core::agent::ActorRef`，已随 T26 落地）。
2. webhook 投递加 `X-IronForge-Event`（kind）与 `X-IronForge-Delivery`（delivery id）头；payload 外层包信封，**原字段原样保留在 `data` 里** —— 老消费者不得破。
3. 修「5xx 视为成功」：接收方 5xx / 429 入队重试（复用 `deliver_retry_job` 的退避），4xx 仍按现有语义处理。
4. 三类事件各有一个测试钉住：信封字段完整、老字段仍在 `data`、5xx 触发重试入队。
5. 序列化需稳定：`schema` 常量、字段顺序无要求但**字段名不得改**；`repo_events` 的读端若受影响，同步兼容（`payload` 内多一层信封属可接受变更，但需在读端保留对旧格式的容忍）。
