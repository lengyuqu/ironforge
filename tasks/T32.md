# Task T32 - 大仓库性能基线（固定数据集 + 阈值）

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。
> 对应差距清单条目：`Git 协议 / 大仓库性能基线`（MISSING，权重 0.75，next_acceptance = 「固定数据集与阈值进入 CI/周期任务」）。

## Task Constraint

**当前状态：仓库里没有任何 `benches/` 目录，没有固定数据集，没有阈值，也没有回归报告。** 这意味着两件事无法回答：

1. 一个 5 万 commit、50 万文件、2 GB 的仓库推进来，IronForge 是 3 秒还是 3 分钟？
2. 下次改动 `upload-pack` 之后，有没有变慢？

本任务建立**可重复、可在 CI 跑、有绝对数字**的基线，不做性能优化。优化是后续任务的事——没有基线就没有优化的判据。

## 硬约束（先说清楚，避免走错路）

1. **不得修改 `Cargo.toml` / `Cargo.lock`。** 因此**不能**用 `[[bench]]` + criterion。基线写成 `crates/rg-git/tests/perf_baseline.rs` 里的 `#[ignore]` 测试，用 `std::time::Instant` 手工计时。
2. **不得修改 `scripts/`**（PLANNING.md 共享禁区）。数据集生成逻辑必须是 Rust 代码（测试 fixture 模块），不是 shell 脚本。
3. **不得引入新的 dev-dependency。** `tempfile` 已在 `rg-core` 的 dev-deps 里；若 `rg-git` 没有，把基线测试放在**已有 tempfile 的 crate**，或在测试内用 `std::fs` 手写临时目录管理。先读 `crates/rg-git/Cargo.toml` 确认。
4. **数据集必须可重建且体积可控。** 用固定种子（`0x1R0N`）的确定性伪随机，禁止 `rand`（未在依赖里）。用简单的 LCG 或 `DefaultHasher` 派生即可。

## 要做的四件事

### 1. 三档固定数据集生成器

在 `crates/rg-git/tests/perf_fixture.rs`（`mod perf_fixture;` 由基线测试引入，或用 `#[path]`）实现：

```rust
pub struct DatasetSpec {
    pub name: &'static str,
    pub commits: usize,
    pub files: usize,
    pub file_bytes: usize,   // 平均文件大小
    pub dirs: usize,
}

pub const SMALL:  DatasetSpec = /* 100 commits / 2_000 files  / 1 KiB  / 20 dirs  */;
pub const MEDIUM: DatasetSpec = /* 2_000 commits / 20_000 files / 4 KiB  / 200 dirs */;
pub const LARGE:  DatasetSpec = /* 20_000 commits / 200_000 files / 8 KiB / 1_000 dirs */;
```

要求：
- 用 `gix` 或直接写 git 对象（**优先 `gix`**，避免引入 git CLI；若必须用 CLI，走 `GitCommandGateway`）
- 文件内容由 path + commit 序号派生，保证两次生成字节一致
- 生成到 `tempfile::TempDir`，测完自动清理
- **LARGE 加 `#[ignore]` 且默认不跑**（磁盘 1.6 GB 级），只手工触发

### 2. 五个测量点

| # | 测量 | 接口 | 为什么测这个 |
|---|------|------|------------|
| 1 | `push` 首推（全量对象） | `receive-pack` 路径 | 迁移大仓库的第一个动作，最痛 |
| 2 | `push` 增量（改 1 文件） | `receive-pack` 路径 | 日常高频，退化最容易不被发现 |
| 3 | `clone`（空目录全量拉） | `upload-pack` 路径 | 新成员入职、镜像同步 |
| 4 | `log` 首页（100 条） | 引用遍历 + commit 解析 | Web 首屏 |
| 5 | `tree` 根目录 + 深层目录 | `gix` tree 遍历 | 浏览器性能 |

每项输出：`{dataset, operation, elapsed_ms, bytes, p50/p95 if repeated}`。每项至少跑 3 次取中位数（`LARGE` 只跑 1 次）。

### 3. 阈值与退化判据

写进 `perf_baseline.rs` 的常量表：

```rust
// (dataset, operation) -> 上限毫秒
pub const THRESHOLDS: &[(DatasetName, Operation, u64)] = &[
    (Medium, PushInitial,  /* 实测后填 */ ),
    (Medium, PushIncremental, /* ... */),
    (Medium, Clone,        /* ... */),
    ...
];
```

- **第一次运行后按实测定值，再乘 1.5 作为上限**（给 CI 机器抖动留余量）
- 断言 `elapsed <= threshold`，失败信息里必须打印实测值与阈值
- 同时记录环境指纹（CPU 型号、核数、磁盘类型、`rustc -V`），写进报告——不同机器数字不可比，必须标定

### 4. 报告

`docs/plans/T32-baseline-report.md`，必须包含：

- 三档数据集的**实际生成耗时与磁盘占用**（证明数据集本身可用）
- 5 个测量点的**实测毫秒数**（表格：small / medium / large × 5）
- 与 Gitea 1.26.4 的**同机对比**（若本机有 docker，起一个 Gitea 跑同样数据集；起不来就明确写「未做同机对比」并把原因写清楚，不要估）
- 阈值表与被选定的依据
- 已知瓶颈的观察（例如 pack 是否流式、是否有二次 O(n) 扫描）——**只记录，不修**
