## Task Constraint

`crates/rg-http/tests/auto_merge_pinned_head_tests.rs:138` 的
`an_auto_merge_whose_head_moved_waits_for_the_next_evaluation` 是 **flaky**：

- T24 全量跑 `cargo test -p rg-http` 时红过一次
- 单独跑该二进制 3/3 绿
- 第二次全量完整通过

**修法必须是确定性的**（消除竞争或让它可确定观察），**不许加重试、不许加 `sleep`、不许把断言放宽**。加重试只是把 flake 藏起来，下次换台机器照样红。

## 已收集的线索（`04e4aa5` 基线，我已核实）

1. 测试流程：
   ```
   commit a.txt           → reviewed sha
   open_pr                → number
   enable_auto_merge      → 记录 reviewed
   commit b.txt           → moved sha，**触发 push handler**
   record_head(number, &reviewed)   // 手动把 head 钉回旧值
   try_auto_merge(..)     → 期望 status="pending"、main 不动、PR 仍 open、auto_merge 仍开
   record_head(number, &moved)
   try_auto_merge(..)     → 期望合并成功
   ```

2. `World::commit`（`:72`）走 **HTTP API** `POST /repos/{owner}/work/contents/{path}`，因此会进 push handler。

3. push handler 里有两处 auto-merge 相关触发（`crates/rg-http/src/lib.rs:3579` 和紧随其后），**都是 `.await` inline，不是 spawn**：
   ```rust
   rg_core::pull_request::try_auto_merges_for_head_commit(db, repo_root, repo_id, &update.new_sha).await
   rg_core::pull_request::merge_queue::process_for_head_commit_with_ci(...).await
   ```

4. 该测试文件里的 `World` 注释提到「tests of one process share a database (CLAUDE.md pitfall 23)」，`pr()` 已按 repo 过滤。

## 你要做的

### 1. 先复现，拿到失败率
- 循环跑该测试二进制 **至少 20 次**（`cargo test -p rg-http --test auto_merge_pinned_head_tests` 重复执行，或用 `--test-threads` 变化制造压力）
- 记录：跑了几次、红了几次、红的那次的**完整断言失败信息**（不是只记"红了"）
- 如果 20 次都绿，**加大并发**（`--test-threads=8`）或与其它 auto_merge 相关测试并行跑，直到复现为止。**复现不了就停下报告**，不要凭猜测改代码。

### 2. 定位根因（要有证据，不是推测）
候选方向（按可能性排序，自己验证）：
- **A**：`try_auto_merges_for_head_commit` 内部有 spawn / 后台任务，`w.commit()` 返回时它还没跑完，稍后改了 PR 状态
- **B**：`commit b.txt` 那次 push handler 的评估**已经把 PR 合并或改了 auto_merge_enabled**（如果它 pin 的是"当前 head"而不是"已批准的 head"）
- **C**：`record_head` 与 push handler 的评估之间有写冲突（同一行被别人改过）
- **D**：共享数据库下另一个测试的 PR 被 `try_auto_merges_for_head_commit` 按 `head_sha` 扫到（注意它是按 **head_sha** 找 PR，不是按 repo+number——这正是跨测试干扰的完美路径）

**D 我认为最可疑**：`try_auto_merges_for_head_commit(db, repo_root, repo_id, &update.new_sha)` 虽然带 `repo_id`，但如果别的测试在**同一个 repo**（`alice/work`）上并行跑，同一个 sha 不会撞；但**同一测试文件的多个测试都往 `alice/work` 推分支**，如果某个测试的 sha 恰好等于另一个的，就会互相干扰。先验证这条。

### 3. 修（按根因选，plan 里说明为什么选这个）
- 若是 **A/B**：让测试在 `w.commit()` 之后**显式等待该 PR 的 auto-merge 评估完成**（例如轮询 `auto_merge` 相关字段直到稳定，或调用暴露的同步入口），而不是盲等
- 若是 **C**：把测试里的读-改-写改成一次原子操作
- 若是 **D**：给每个测试独立的 repo（`World::new(name)` 似乎已这么做，核实是否真的隔离），或让 `try_auto_merges_for_head_commit` 的扫描再按 `repo_id` 收紧

**不许**：`tokio::time::sleep(固定值)`、`retry until pass`、把 `assert_eq` 改成 `assert!(.. || ..)`。

### 4. 验证
- 修后循环跑 **30 次**（含 `--test-threads=8` 的压力跑），全绿
- 若根因是 D，额外验证：单独跑该测试 30 次 + 与该文件其它测试并行 30 次，都绿
- 顺带检查同文件其它测试是否有同样的隐患（列出，但**不要顺手全改** —— 超出本次范围就单独记）

## Result（2026-11-18）

- **根因 A（测试问题，非生产 bug）**：`World::commit` 走 HTTP `/contents`，该 handler 用
  `tokio::spawn` 跑后置钩子（`lib.rs:3402`）；钩子的 `sync_pr_head_on_push` 会把记录的
  `head_sha` 推到新提交，`try_auto_merges_for_head_commit` 随即合并 PR。测试手工把记录写回
  旧值，两个写者在抢同一行——跑赢钩子才绿。D（跨测试按 sha 干扰）已排除（每测试独立 SQLite）。
- **修法**：分支移动改走 `rg_core::repo::service::create_or_update_file_with`（不 spawn 钩子），
  无后台写者；断言一行未改，无重试/sleep/轮询。
- **复现**：改前 8 路并发 × 80 次失败 15 次（目标用例 14 次，`left: "merged" / right: "pending"`）；
  改后同负载 0/80，顺序 30/30、单用例 30/30 全绿。
