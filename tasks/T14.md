# Task T14 - [#15 第二步] ops 签名批量放宽：org_ops + user_ops

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。

## Task Constraint

T13 打通了「事件写入可在事务内」的单条链路。#15 的后续是**按文件批量收敛** ops 层签名，让更多写路径能进事务。

**本任务只做两个文件**：`crates/rg-db/src/ops/org_ops.rs`（25 处）与 `crates/rg-db/src/ops/user_ops.rs`（26 处）。共 **51 处 `&DatabaseConnection`**，两个文件都**没有** `db.begin()` / `db.transaction()` 调用（已核实），是最干净的一批。

**不做** `pipeline_ops.rs`（38 处里有 7 处 `db.begin()`，那些函数必须保留 `&DatabaseConnection`，需要逐函数判断，留给下一轮）。

## 要求

### 1. 放宽方式（最小 diff）

```rust
// 改前
pub async fn list_org_repos(db: &DatabaseConnection, org_id: i64) -> Result<Vec<_>, DbErr>

// 改后
pub async fn list_org_repos<C: ConnectionTrait>(db: &C, org_id: i64) -> Result<Vec<_>, DbErr>
```

- **参数名保留 `db`**，只改类型并加泛型 —— diff 越小越好 review。
- 用 `sea_orm::ConnectionTrait`（文件顶部若只 `use sea_orm::*;` 则无需新增 use）。
- 泛型参数名统一用 `C`。

### 2. 编译驱动，不要盲改

这类改动会有**连锁**：函数 A 放宽后，如果它内部调了函数 B（B 仍是 `&DatabaseConnection`），把 `&C` 传给 B 会编译失败。处理顺序：

1. 先改一批
2. `cargo check -p rg-db` 看错误
3. 错误分两类：
   - **被调用方也该放宽** → 一并放宽
   - **当前函数确实需要 `DatabaseConnection` 特有方法**（`begin` / `transaction` / `clone` / `ping` 等）→ **保留原签名**，在 plan 里列出函数名与原因
4. 反复直到 `cargo check` 干净

**不要**为了让编译通过而给这些函数加 `where Self: Sized` 之类的花招，也不要引入 trait 对象。

### 3. 不许改语义

- 禁止改动任何 SQL 条件、排序、错误信息、返回值。
- 禁止顺手优化或重命名。
- 调用方（`rg-core` / `rg-http`）**不应该需要改动** —— `DatabaseConnection` 实现了 `ConnectionTrait`，`&DatabaseConnection` 可以直接传给 `&C`。如果发现调用方必须改，说明改动方式有问题，**停下报告**。

### 4. 统计口径（用于验收）

改动前记录：`grep -c '&DatabaseConnection' crates/rg-db/src/ops/org_ops.rs` = 25、`user_ops.rs` = 26。
改动后应该是：可放宽的全部变成 `&C`，保留的仍然计数。**报告里给改前/改后的两个数字与保留清单**。
