# Task T13 - [#15 第一步] 事件写入可在事务内：签名放宽 + issue.opened 最小闭环

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。

## Task Constraint

#15 的目标是 outbox（业务写 + 事件写同事务、至少一次投递）。**但 outbox 表不是第一步**——第一步是先让事件写入**能够在事务里发生**。当前类型系统不允许：`repo_event_ops::append` 的 `db` 写死 `&DatabaseConnection`，而 SeaORM 的 `Transaction` 不 `Deref` 到它。

**本任务只做一条链路（`issue.opened`）**，把「事务内写事件 + 事务外投递」跑通并验证。**绝对不要**试图一次改完 498 个签名。

已核实（`c3b9998` 时点）：

```
append(db: &DatabaseConnection, repo_id, event_type, payload) -> Result<i64>      // repo_event_ops.rs:7
record_envelope(db: &DatabaseConnection, repo_id, event, envelope)                 // webhook/service.rs:310（private）
dispatch(db, repo_id, event, envelope) { record_envelope(..); list_active_by_repo_and_event(..); for hook { spawn } }  // :317
trigger_event(db, repo_id, event, payload) = event_actor + EventEnvelope::new + dispatch   // :251
record_event(...)  = 同上 + record_envelope                                       // :274
trigger_event_quietly(...) = record_event + debug                                  // :295
```

`issue/service.rs:56 begin → :59 commit → :70 trigger_issue_opened`（**事件在提交之后才写**，崩溃窗口内业务已提交、事件永久丢失）。

## 要求

### 1. 签名放宽（只放宽这一条链，不做全仓）

- `repo_event_ops::append` → `pub async fn append<C: ConnectionTrait>(conn: &C, ...)`（SeaORM 的 `ConnectionTrait`，`DatabaseConnection` / `DatabaseTransaction` / `DatabaseConnectionProxy` 都实现它）
- `repo_event_ops::latest_id` 如果只被读路径用，**保持原样**，不要顺手改（减少改动面）。
- `webhook/service.rs::record_envelope` → 同样放宽为泛型。

**注意**：`record_repo_event`（`webhook/service.rs:227`）也在这条链上，需要一起放宽；但它的其他调用点（如果有）保持能编译即可，不要改语义。

### 2. 两个新函数（这是本任务的核心）

在 `webhook/service.rs` 里拆出：

```rust
/// 只写事件日志，不投递。可在事务内调用。
pub async fn record_event_in_txn<C: ConnectionTrait>(
    conn: &C, repo_id: i64, event: &str, payload: &Value,
) -> Result<()>;

/// 只投递，不写日志（日志已由 record_event_in_txn 写过）。事务提交后调用。
pub async fn deliver_event(
    db: &DatabaseConnection, repo_id: i64, event: &str, payload: &Value,
) -> Result<()>;
```

- `deliver_event` **不能**再写一次 `repo_events`（否则提交后事件写两遍、cursor 跳两格）。
- `deliver_event` 内部查 webhook 并 spawn 投递，与现有 `dispatch` 的后半段一致。
- `trigger_event` 改为 `record_event_in_txn(db) + deliver_event(db)`，**行为与现在完全等价**（对外签名不变，13 个 `trigger_*` 命名糖零改动）。

### 3. `issue.opened` 走新路径

`crates/rg-core/src/issue/service.rs::create_issue`：

```rust
let txn = db.begin().await?;
// ... 现有业务写入（issue 行、label、assignee、watch ...）
record_event_in_txn(&txn, repo_id, "issue.opened", &payload).await?;   // 移到 commit 之前
txn.commit().await?;
deliver_event(&db, repo_id, "issue.opened", &payload).await?;          // commit 之后
```

- **payload 必须与现在一模一样**（字段、顺序都不变），只是写入时机提前。
- 如果 `create_issue` 里现在有多条 trigger（比如同时发 `issue.opened` 和 `notification`），**只移 `issue.opened` 到事务内**，其他的保持原样并在 plan 里列出——本任务是证明机制可行，不是全量迁移。
- `event_actor(db, payload)` 查 actor 时若需要 DB 读，用事务连接（`&txn`）而不是 `db`，避免读到不一致快照。

### 4. 验证（这一条最关键）

必须有一个**能失败**的测试证明机制生效：

1. **回滚不写事件**：构造一个在 `record_event_in_txn` 之后、`commit` 之前失败的场景（注入错误或用一个会失败的业务写），断言 `repo_events` 里**没有** `issue.opened`、且 webhook receiver 没收到请求。**这个测试在改动前必须是失败的**（先用旧代码跑一次证明它 red，再改）。
2. **提交则写事件**：正常创建 issue → `repo_events` 有 `issue.opened`、webhook 收到、cursor 单调。
3. **不重复写**：一次创建 issue，`repo_events` 里 `issue.opened` **只有一行**（防止 `deliver_event` 又写一次）。
4. **兼容性**：其他 12 个 `trigger_*` 调用路径的既有测试全绿（证明 `trigger_event` 等价改造没破坏别处）。
