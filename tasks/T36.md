## 要做的五件事

### 1. 建立核对基线（先于任何代码改动）

用 `cnb` CLI 把这些真实数据存成 JSON 快照，放进 `crates/rg-core/tests/fixtures/cnb/`（或临时目录，不入库）：

```sh
cnb issues list-issues --repo <owner>/<repo> --page-size 100 -v > issues_list.json
cnb issues get-issue --repo <owner>/<repo> --number <N> -v > issue_N.json
cnb issues list-issue-comments --repo <owner>/<repo> --number <N> -v > issue_N_comments.json
cnb pulls list-pulls --repo <owner>/<repo> --page-size 100 -v > pulls_list.json
```

**先跑，看清真实字段**，再对照 `cnb_client.rs` 的 struct 定义。任何字段名/类型不符，就是第一个 bug。

### 2. 逐项字段级对照（这是本任务的主体）

对每类实体，列表形式回答「代码期望 vs 真实返回」：

| 实体 | 字段 | 代码期望 | 真实值 | 结论 |
|---|---|---|---|---|

重点核对 `cnb_client.rs` 里**没有实测依据**的部分：
- `CnbPull` / `CnbPullRef` 的全部字段（PR 是明确未验证的）
- `CnbComment`（issue 评论的作者/时间/body 字段名）
- labels 的形态（代码注释说「有些端点发字符串而不是对象」，实测哪些端点发哪种）
- 分页：`X-Cnb-Page` 等 header 的实际值与 `total/totalPages` 是否一致

### 3. 端到端真机导入

起一个干净的 IronForge 实例（`cargo run -p rg-cli -- serve` 或已编译二进制 + 独立数据目录），用 API 触发：

```sh
POST /api/v1/imports
{ "platform": "cnb", "source_url": "https://cnb.cool/<owner>/<repo>", "target_owner": "...",
  "auth_token": "<从 ~/.cnb/token 解析出的裸 token>", "import_repo": true,
  "import_issues": true, "import_pull_requests": true, "import_labels": true }
```

然后**直接查 SQLite** 核对落库（不许只看 `import_tasks.stats`——GitLab 那次就是 stats 对、数据是孤儿）：

```sql
SELECT id, number, title, state FROM issues WHERE repo_id = <id>;
SELECT id, body, user_id FROM issue_comments WHERE issue_id = <id>;
SELECT id, number, title, head_branch, base_branch, state FROM pull_requests WHERE repo_id = <id>;
SELECT id, pull_request_id, action, body FROM pr_reviews WHERE pull_request_id = <id>;
SELECT name FROM labels WHERE repo_id = <id>;
```

**特别检查**：评论的外键是否指向真实存在的父行（GitLab 的坑就是这个）。用

```sql
SELECT COUNT(*) FROM issue_comments c LEFT JOIN issues i ON c.issue_id = i.id WHERE i.id IS NULL;
SELECT COUNT(*) FROM pr_reviews r LEFT JOIN pull_requests p ON r.pull_request_id = p.id WHERE p.id IS NULL;
```

两个都必须为 0。

### 4. 修掉所有发现的缺陷

每个缺陷一个独立 fix，commit message 说明「真实返回是什么 / 代码假设是什么 / 怎么改的 / 怎么验证的」——照 `a4c47b81` 的写法。

已知需要确认的点（先验证再改，不要预先假定是 bug）：
- `parse_cnb_url` 对 `https://cnb.cool/owner/repo.git` / 无 `.git` / 带尾斜杠 / 带子路径 的处理
- `get_issue` 的 N+1：是否需要重试与退避（CNB 限流行为未知，实测观察）
- PR 的 `head`/`base` ref 形状：是不是 `ref` 字段嵌在 `head` 里，字段名叫 `sha` 还是 `ref` 还是 `branch`
- 评论时间格式与 `parse_datetime_or_now` 的兼容性（CNB 用 `2026-11-24T15:04:04Z`）
- 正文为空的 issue（`body: ""` 而非 `null`）会不会被当成「无正文」而漏掉
