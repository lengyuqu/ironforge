# Task T31 - [#63·第四步] 让 `partial` 反映真实索引质量

> 本文件是该任务状态的唯一权威；`TASKS.md` 只放镜像索引。

## Task Constraint

T29 的 `partial` **恒为 `true`**，理由是「T28 没存每 commit 的解析失败数，`partial: false` 是无证据的断言」。

这个理由是诚实的，但代价是**这个字段现在零信息量**——无论索引多干净都返回 `true`，调用方无法区分「完整索引」和「有 16 个文件解析失败」。

**关键发现：失败信息本来就有，只是没统计。** `crates/rg-core/src/search/outline/mod.rs:166` 的 `Outline` 结构：

```rust
pub struct Outline {
    pub language: Language,
    pub items: Vec<OutlineItem>,
    pub truncated: bool,          // 命中 item 上限，有丢弃
    pub error: Option<String>,    // 解析失败原因；items 可能仍有部分结果
}
```

所以本任务**不改 `outline` 模块**（T28 已禁止），只在 `index_commit` 里统计这两个信号，存进 `symbol_commits`，让 `partial` 变成有依据的判断。

## 要做的四件事

### 1. 迁移：`symbol_commits` 加三列（32 → 33）

```
files_total      INTEGER NOT NULL DEFAULT 0   -- 参与索引的文件数
files_failed     INTEGER NOT NULL DEFAULT 0   -- outline.error.is_some() 的文件数
files_truncated  INTEGER NOT NULL DEFAULT 0   -- outline.truncated 的文件数
```

- `up` 幂等（`has_column` 守卫）、`down` 可回滚（删列）
- **历史行的默认值 0 会读作「完整」**——这是错的（旧索引没统计过，不知道是否完整）。所以迁移里**必须把已存在的行标记为未知**：用一个哨兵值，建议 `files_total = -1`（表示"未统计"），并在查询侧把 `-1` 视为 `partial: true`（无法证明完整）。

  **如果你认为哨兵值不如加一个 `stats_known` 布尔列干净，自己选并说明理由**，但必须解决「历史行不能假装完整」这个问题。

- **SQLite 加列带 DEFAULT 是允许的；MySQL/PG 也要能跑**（三后端 up+down）

### 2. `index_commit` 统计

在遍历文件时累计：

```rust
let mut files_total = 0u32;
let mut files_failed = 0u32;
let mut files_truncated = 0u32;
// 每个成功读取的文件：
files_total += 1;
if outline.error.is_some() { files_failed += 1; }
if outline.truncated { files_truncated += 1; }
```

写进 `symbol_commits` 的 upsert（重复索引时覆盖为新值）。

### 3. `find_symbols` 的 `partial` 与 `limitations`

```rust
let stats = /* 从 symbol_commits 读三列 */;
let partial = stats.total < 0                      // 未统计（历史行）
    || stats.failed > 0
    || stats.truncated > 0
    || /* svelte 降级这条永远为真，见下 */;
```

**svelte 那条要处理**：`limitations` 里原本有「svelte 只解析 `<script>`」，这是**静态为真的语言限制**，不是"这次索引有问题"。所以：

- `limitations` **永远**包含静态语言限制（svelte / Rust 宏 / TS `obj[key]` / Go 接口等）——它们描述的是**能力的边界**，不是这次索引的状态
- `partial` **只**反映"这次索引本身的完整性"（失败/截断/未统计）

**别把两件事混在一起**：`partial: true` 因为 svelte 文件多而恒真，那是把"能力限制"当"数据缺陷"，和现在恒 `true` 一样没有信息量。

（当前实现是把 svelte 那条算进 `partial` 的理由之一，本任务要把它拆开。先读 `symbol_query.rs` 确认现在怎么写的。）

### 4. 动态 `limitations`

当 `files_failed > 0`，追加一条**带具体数字**的：

```
"N files failed to parse and are only partially indexed"
```

当 `files_truncated > 0`：

```
"M files exceeded the item cap and were truncated"
```

`files_total < 0`（未统计）时：
```
"this commit was indexed before completeness stats were recorded; completeness is unknown"
```

## 验证

1. **全新索引（干净仓库）**：取一个能全部解析的 commit → `partial == false`，`limitations` 里仍有静态语言限制（svelte/宏等），但**没有** "N files failed"
2. **有解析失败**：构造一个含坏文件的 commit（或找一个真实的 `web/**/*.test.svelte.ts`）→ `partial == true`，`limitations` 含具体数字
3. **历史行**：手工插一条 `files_total = -1` 的 `symbol_commits`（或不带统计列的旧行）→ `partial == true` 且 `limitations` 含"completeness is unknown"
4. **重复索引更新统计**：同一 commit 索引两次，第二次统计值覆盖第一次（不是累加）
5. **迁移**：SQLite / PG / MySQL up+down 各跑
6. **既有测试全绿**：`ai_symbol_query_tests` 里原来断言 `partial == true` 的用例要按新语义改（改成断言"有失败时 true"），**不要简单删断言**
